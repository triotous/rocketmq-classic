# ADR-0001: Initial remoting transport ownership

- Status: accepted for the Phase 3 partial transport implementation; Java parity is not claimed.
- Date: 2026-09-25

## Context

The pinned RocketMQ Java client 5.5.1 uses Netty channels, a response table keyed by opaque, `ResponseFuture` timeout/callback handling, processor dispatch, TLS setup, and explicit client shutdown. The Rust transport needs one terminal owner for each request and bounded, joinable local work without blocking frame reads. This ADR describes the current Rust mapping, not a waiver for missing Java behavior.

## Decisions

- `RemotingClient::invoke` accepts an absolute Tokio `Instant` deadline and owns one pending entry keyed by opaque and connection generation. A pending guard removes the entry if its future is cancelled. Responses, generation closure, expiry, and shutdown complete the oneshot through remove-before-complete ownership. `ClientConfig` exposes Java-derived connect timeout, async/oneway admission, worker/callback executor sizes, idle and reconnect controls, SOCKS5 and socket/watermark settings; defaults are audited against Java 5.5.1 `NettyClientConfig` but not every setting is behaviorally implemented yet.
- Opaque IDs use wrapping `AtomicI32`; insertion probes past occupied IDs, so wrap never overwrites a live request.
- Address keys lowercase DNS/IP text and preserve bracketed IPv6 spelling. One per-key async gate provides connection single-flight; each published connection owns a bounded write queue, one reader/writer task and a join handle.
- Inbound commands enter a bounded queue and configured worker set. A registered raw-code processor executes for one-way inbound requests but those requests never receive a response; processors without an explicit executor use the configured worker pool; per-registration caller-owned executors may route tasks, and executor rejection maps to SYSTEM_BUSY; processors may reject requests or produce an opaque-preserving response for normal requests. An optional default processor handles unmatched request codes while exact-code registration takes precedence. Unsupported and overload codes follow the matching Java response family. RPC hooks and a request pipeline are available; the pipeline receives remote address and connection generation and may return a typed abort (response code/remark) or failure (SYSTEM_ERROR). Existing infallible RPC hooks remain source-compatible; new fallible hook methods can abort with a response code/remark or map failures/panics to SYSTEM_ERROR; after hooks run even when the processor returns no response, with optional response context. This is not Netty `ChannelHandlerContext` parity; full Java RPC-hook AbortProcessException/exception ordering (typed abort and SYSTEM_ERROR outcomes are now supported), Java-owned executor lifecycle/thread behavior, exact RejectedExecutionException behavior and GO_AWAY shutdown/reconnect flows remain unmapped.
- TLS and plain TCP are explicit modes. Rustls validates trust and host names, preserves DNS for SNI, accepts caller-provided CA PEM and optional client certificate/key PEM, and shares the connect deadline with handshake. Native trust roots are used when no custom CA is supplied.
- Async callback invoke reserves Java-sized semaphore admission within its deadline and runs callbacks through a configurable bounded worker queue or a caller-supplied `CallbackExecutor` corresponding to Java `setCallbackExecutor`; caller-executor rejection runs the callback inline. Disabling the callback executor currently runs callback code in the invoke task, not a Netty event loop. Queue saturation falls back to the caller task. Success and terminal errors call one of `operation_succeed`/`operation_fail` followed by `operation_complete`; an additional context callback exposes the original request, optional response/error, send status, timeout flag and elapsed duration. Async pending-response expiry uses Java's +1 second scan grace. Exact send-failure taxonomy and all `ResponseFuture` lifecycle details remain unmapped. SOCKS5 supports no-auth and username/password handshakes and shares the connect deadline. Configured TCP and SOCKS5 TCP send/receive buffer sizes are applied with socket-level options; write high/low watermarks track queued outbound bytes with hysteresis, while pooled allocator configuration is explicitly rejected as unsupported. Idle connections are closed by the owned scheduler; NameServer last-response age is also scanned. `GO_AWAY` retries once under the original deadline when enabled, then returns `TransportError::GoAway`; Java channel-wrapper edge behavior still needs source-mapped tests. NameServer APIs track configured/available lists, select a round-robin address, fail over across addresses after connection failures, and scan connect availability on the configured interval. A successful response marks an address available only while that same connection generation remains current; socket close clears its chosen/available state. Java's randomized list update, exact wrapper recovery and scan-executor semantics are not fully reproduced. Shutdown rejects new calls, signals processors and timers, closes sockets, completes pending calls, and joins client-owned tasks. Repeated calls share one shutdown completion.

## Java source mapping and current gaps

| Java 5.5.1 source | Rust mapping | Gap/status |
|---|---|---|
| `NettyRemotingClient.invoke`, `invokeSync`, `invokeAsync`, `invokeOneway`, `setCallbackExecutor`; `NettyRemotingAbstract.invokeSyncImpl` | `invoke`, `invoke_sync`, `invoke_async`, `invoke_oneway`, `set_callback_executor`, `InvokeCallback`, `CallbackExecutor`, `ClientConfig` | Partial: deadline callback/executor, caller executor routing/rejection fallback, duration wrapper and semaphore admissions exist; callback metadata and +1-second async timeout grace are represented, while Java blocking errors and exact send/timeout taxonomy remain. |
| `NettyRemotingAbstract.invoke0`, `processResponseCommand`, `scanResponseTable`; `ResponseFuture` | `PendingEntry`, `PendingGuard`, `timeout_scheduler` | Partial: core correlation, timeout and cancellation ownership; async callback path uses +1-second grace and exposes callback metadata, while detailed send-failure callback taxonomy remains. |
| `ChannelWrapper`, `getAndCreateChannel*`, `closeChannel`, `SocksProxyConfig`, channel events, NameServer methods | `Address`, `SocksProxyConfig`, `ChannelEventListener`, connection generations, `is_channel_writable`, `is_address_reachable`, `close_channels` | Partial: SOCKS5, idle closure/events and basic NameServer list/scan/selection/failover added; reachability uses async connect and writability reflects configured outbound-byte watermarks or queue capacity, not Netty channel watermarks; exact chosen-channel semantics and Java event executor lifecycle/overload behavior remain; Rust events are delivered asynchronously through a bounded single-worker queue. |
| `NettyRemotingAbstract.processRequestCommand`, processor table, RPC hooks/pipeline, `GO_AWAY` | `RequestProcessor`, `RpcHook`, `RequestPipeline`, `TransportError::GoAway` | Partial: hooks/pipeline/reject, default processor fallback and one GO_AWAY retry added; pipeline context/typed abort is covered by loopback tests, but Netty context, Java-owned per-code/default executor lifecycle and exact rejection/reconnect semantics remain. |
| `NettyRemotingClient` TLS configuration and `TlsHelper` | `TransportMode::Tls(TlsConfig)` | Partial: trust/hostname/client identity are supported; Java TLS reload/configuration flags and event behavior remain unmapped. |
| `NettyRemotingClient.shutdown` | `RemotingClient::shutdown` | Partial: owned Rust tasks are joined; full Java resource/configuration lifecycle parity is outstanding. |

## Verification

Scripted TCP/TLS loopback tests in `crates/rocketmq-classic-remoting/tests/transport.rs` plus private unit race tests cover automated subsets of P3-V01/V02/V03/U01, including stale generations, opaque wrap, cancellation/timeout/response/shutdown terminal ownership, saturation, TLS trust/hostname failures, caller callback executor routing/rejection, context-aware pipeline execution, typed abort mapping and fallible RPC-hook abort/error, outbound before-hook execution after connection establishment, Java-style pipeline/after-hook handling on ordinary inbound before-hook failure, and absent-response after-hook behavior. They are offline transport checks, not Broker behavior, and do not establish full Java parity. Java overload/API surfaces, callback metadata and exact timeout timing, Java-owned per-processor executor lifecycle, channel event executor lifecycle, actual Netty pipeline context and complete Java RPC-hook ordering/exception semantics, TLS property/config-file/reload flags, pooled allocator and worker-group controls remain incomplete. Watermark behavior is covered locally but intentionally differs from Netty's transport-level writability. P3-V04 remains reserved for Phase 19. See `docs/compatibility/JAVA_5_5_1_COMPATIBILITY.md` for the matrix and gaps.
