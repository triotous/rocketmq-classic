# ADR-0001: Initial remoting transport ownership

- Status: accepted for the Phase 3 partial transport implementation; Java parity is not claimed.
- Date: 2026-09-25

## Context

The pinned RocketMQ Java client 5.5.1 uses Netty channels, a response table keyed by opaque, `ResponseFuture` timeout/callback handling, processor dispatch, TLS setup, and explicit client shutdown. The Rust transport needs one terminal owner for each request and bounded, joinable local work without blocking frame reads. This ADR describes the current Rust mapping, not a waiver for missing Java behavior.

## Decisions

- `RemotingClient::new` / `with_config` validates configuration and stores startup receivers without starting background tasks. Applications call `start()` inside an active Tokio runtime before using transport operations; start is idempotent, operations reject pre-start use, and shutdown before start prevents a later start.
- `RemotingClient::invoke` accepts an absolute Tokio `Instant` deadline and owns one pending entry keyed by opaque and connection generation. A pending guard removes the entry if its future is cancelled. Responses, generation closure, expiry, and shutdown complete the oneshot through remove-before-complete ownership. `ClientConfig` exposes Java-derived connect timeout, async/oneway admission, worker/callback executor sizes, idle and reconnect controls, SOCKS5 and socket/watermark settings; defaults are audited against Java 5.5.1 `NettyClientConfig` but not every setting is behaviorally implemented yet.
- Opaque IDs use wrapping `AtomicI32`; insertion probes past occupied IDs, so wrap never overwrites a live request.
- Address keys lowercase DNS/IP text and preserve bracketed IPv6 spelling. One per-key async gate provides connection single-flight; each published connection owns a bounded write queue, one reader/writer task and a join handle.
- Inbound commands enter a bounded queue and configured worker set. A registered raw-code processor executes for one-way inbound requests but those requests never receive a response; processors without an explicit executor use the configured worker pool; per-registration caller-owned executors may route tasks, and executor rejection maps to SYSTEM_BUSY; processors may reject requests or produce an opaque-preserving response for normal requests. An optional default processor handles unmatched request codes while exact-code registration takes precedence; `ProcessorRegistration` and `with_processor_table` provide lock-protected live registration-table inspection/mutation corresponding to Java `getProcessorTable()`. Unsupported and overload codes follow the matching Java response family. RPC hooks (with identity suppression, optional Java-`equals`-style equality keys, snapshot inspection, lock-protected live-list mutation, identity/equality-key removal and explicit clear-all) and a composable request pipeline (`pipe_request_pipeline` executes the newly supplied source stage before the existing pipeline) are available; the pipeline receives remote address and connection generation and may return a typed abort (response code/remark) or failure (SYSTEM_ERROR). Existing infallible RPC hooks remain source-compatible; new fallible hook methods can abort with a response code/remark or map failures to SYSTEM_ERROR inbound / `TransportError::RpcHook` outbound; panics are not swallowed on outbound paths and propagate as Java does, while inbound processing catches them at the request-task boundary; after hooks run even when the processor returns no response, with optional response context. Outbound before hooks run after connection establishment but before async admission (as in Java's `invokeImpl` ordering), and GO_AWAY retry suppresses duplicate hooks. This is not Netty `ChannelHandlerContext` parity; full Java RPC-hook AbortProcessException/exception ordering (typed abort and SYSTEM_ERROR outcomes are now supported), Java-owned executor lifecycle/thread behavior, exact RejectedExecutionException behavior and GO_AWAY shutdown/reconnect flows remain unmapped.
- TLS and plain TCP are explicit modes. `TransportMode::from_java_properties` maps Java `tls.enable` and enforcing-mode defaults; `TlsConfig` models Java client `tls.test.mode.enable` (default true) and `tls.client.authServer` (default false): test mode or disabled auth selects a trust-all server verifier; set both to test mode false/auth server true for chain and hostname verification. Verified mode preserves DNS for SNI, accepts caller-provided CA PEM and optional client certificate/key PEM, loads native trust roots absent a custom CA, and shares the connect deadline with handshake. Java TLS properties/config files can be loaded per configuration, with optional `PrivateKeyDecryptionStrategy`; configuration is a snapshot and does not update existing clients or globally reload at each TLS-context creation as Java does.
- Async callback invoke acquires the connection, executes outbound before hooks, then reserves Java-sized semaphore admission within its deadline and runs callbacks through a configurable bounded worker queue or a caller-supplied `CallbackExecutor` corresponding to Java `setCallbackExecutor`/`getCallbackExecutor`; caller-executor rejection runs the callback inline. When `disable_callback_executor` is set, a custom executor is ignored and callbacks run inline; this remains different from Java's selected Netty event-loop/caller thread. Queue saturation falls back to the caller task. After a channel is established, terminal outcomes call `operation_complete` before `operation_succeed`/`operation_fail`, matching the public Java `invokeAsyncImpl` callback chain; initial connection/TLS setup failures call fail only. An additional context callback exposes the invoke request (the reconstructed retry request after GO_AWAY), optional response/error, send status (Java's public async wrapper exposes the default-true `ResponseFuture.sendRequestOK` on exceptional completion, including internal send failure), timeout flag and elapsed duration. Async pending-response expiry uses Java's +1 second scan grace. Exact send-failure taxonomy and all `ResponseFuture` lifecycle details remain unmapped. SOCKS5 supports no-auth and username/password handshakes and shares the connect deadline. Configured TCP and SOCKS5 TCP send/receive buffer sizes are applied with socket-level options; write high/low watermarks track queued outbound bytes with hysteresis, while pooled allocator configuration enables a bounded per-connection frame-buffer pool (maximum four returned buffers), not Netty's allocator/thread-cache lifecycle. `disable_netty_worker_group` routes inbound processing directly on the connection task instead of queued processor workers; this approximates Java's handler-executor selection but not Netty event-loop identity or scheduling. Idle connections are closed by the owned scheduler. `channel_not_active_interval` is retained as the Java config field but does not trigger an automatic scan: pinned Java `scanChannelTablesOfNameServer()` has no call site, and its NameServer last-response check is therefore not active in the observed client control flow. `GO_AWAY` retries once under the original deadline when enabled, reconstructing a fresh request with Java defaults and preserving code/ext fields/body; hooks are not rerun. Peer/channel-close completion maps to `TransportError::SendRequest` with remote address and no cause, following Java `requestFail`; terminal `GO_AWAY` maps to the same category with a cause. Wrapper identity and reconnect edge behavior still need source-mapped tests. NameServer APIs track configured/available lists, select a round-robin address, fail over across addresses after connection failures, and scan connect availability on the configured interval. A successful response marks an address available only while that same connection generation remains current; socket close clears its chosen/available state. Java's randomized list update, exact wrapper recovery and scan-executor semantics are not fully reproduced. Availability entries for removed addresses remain observable until the next scan prunes them, matching Java's `scanAvailableNameSrv` cleanup timing. Rust rechecks configured-list membership and connection generation before applying an asynchronous probe result, preventing a removed address or stale generation from overwriting current state; Java's per-address executor and wrapper lifecycle differ. Java's protected `scanChannelTablesOfNameServer()` is not called by the pinned client source and is not treated as an active scheduled control flow. Shutdown rejects new calls, signals processors and timers, closes sockets, completes pending calls, and joins client-owned tasks. Repeated calls share one shutdown completion. The explicit `start()` transition launches inbound, callback, channel-event and timer workers on the caller's active Tokio runtime; construction starts none of these workers.

| `NettyRemotingAbstract.invoke0`, `processResponseCommand`, `scanResponseTable`; `ResponseFuture` | `PendingEntry`, `PendingGuard`, `timeout_scheduler` | Partial: core correlation, timeout and cancellation ownership; async callback path uses +1-second grace and exposes callback metadata, while detailed send-failure callback taxonomy remains. |

## Verification

Scripted TCP/TLS loopback tests in `crates/rocketmq-classic-remoting/tests/transport.rs` plus private unit race tests cover automated subsets of P3-V01/V02/V03/U01, including stale generations, opaque wrap, cancellation/timeout/response/shutdown terminal ownership, saturation, TLS trust/hostname failures, caller callback executor routing/rejection, context-aware pipeline execution, typed abort mapping and fallible RPC-hook abort/error, outbound before-hook execution after connection establishment (including a one-way hook-before-admission ordering case), Java-style pipeline/after-hook handling on ordinary inbound before-hook failure, absent-response after-hook behavior, connect-failure channel events, and callback send-status outcomes on peer close. They are offline transport checks, not Broker behavior, and do not establish full Java parity. Java overload/API surfaces, callback metadata and exact timeout timing, Java-owned per-processor executor lifecycle, channel event executor lifecycle, actual Netty pipeline context, live mutable Java hook-list inspection, and exact executor lifecycle, TLS property/config-file loading is implemented, but Java's per-context reload lifecycle remains different. Pooled allocator and worker-group settings have Rust-native partial implementations (bounded frame reuse and direct inbound dispatch, respectively), not Netty allocator or event-loop equivalents. Watermark behavior is covered locally but intentionally differs from Netty's transport-level writability. P3-V04 remains reserved for Phase 19. See `docs/compatibility/JAVA_5_5_1_COMPATIBILITY.md` for the matrix and gaps.
