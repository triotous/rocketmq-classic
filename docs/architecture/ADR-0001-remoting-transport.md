# ADR-0001: Initial remoting transport ownership

- Status: accepted; Phase 3 local transport gates are complete under the documented user dispositions. This ADR does not claim live Broker validation or complete Java/Netty implementation parity; P3-V04 is deferred to Phase 19.
- Date: 2026-09-25

## Context

The pinned RocketMQ Java client 5.5.1 uses Netty channels, a response table keyed by opaque, `ResponseFuture` timeout/callback handling, processor dispatch, TLS setup, and explicit client shutdown. The Rust transport needs one terminal owner for each request and bounded, joinable local work without blocking frame reads. This ADR describes the current Rust mapping, not a waiver for missing Java behavior.

## Decisions

- `RemotingClient::new` / `with_config` validates transport configuration and stores startup receivers without starting background tasks. Applications call `start()` inside an active Tokio runtime before using transport operations; start is idempotent, operations reject pre-start use, and shutdown before start prevents a later start. The lower-level remoting transport config is an immutable construction-time snapshot by the Phase 3 disposition. The core runtime's Java `ClientConfig` is separately exposed as a live mutable handle; see [ADR-0037](ADR-0037-live-runtime-client-config.md).
- `RemotingClient::invoke` accepts an absolute Tokio `Instant` deadline and owns one pending entry keyed by opaque and connection generation. A pending guard removes the entry if its future is cancelled. Responses, generation closure, expiry, and shutdown complete the oneshot through remove-before-complete ownership. The lower-level remoting `ClientConfig` exposes Java-derived connect timeout, async/oneway admission, worker/callback executor sizes, idle and reconnect controls, SOCKS5 and socket/watermark settings; defaults and behavior are covered by the Phase 3 inventory and its named tests. Tokio worker, callback scheduling, ownership and lifecycle differences are accepted and documented.
- Opaque IDs use wrapping `AtomicI32`; insertion probes past occupied IDs, so wrap never overwrites a live request.
- Address keys lowercase DNS names and normalize valid bracketed or unbracketed IPv6 literals, including numeric scope IDs, to a canonical bracketed form. Named IPv6 interface scopes are preserved in the key so the OS resolver can map the interface name during connection lookup. Endpoint splitting uses the final colon, matching pinned Java `NettyRemotingClient.getHostAndPort` for IPv4, hostnames and IPv6; ports 0 through 65535 follow Java's unresolved socket-address range. One per-key async gate provides connection single-flight; each published connection owns an unbounded write queue, one reader/writer task and a join handle.
- Inbound commands enter unbounded queues and a configured worker set, matching Java's unbounded executor backlog. A registered raw-code processor executes for one-way inbound requests but those requests never receive a response; processors without an explicit executor use the configured worker pool; per-registration caller-owned executors may route tasks, and executor rejection maps to SYSTEM_BUSY; processors may reject requests or produce an opaque-preserving response for normal requests. An optional default processor handles unmatched request codes while exact-code registration takes precedence; `ProcessorRegistration` and `with_processor_table` provide lock-protected live registration-table inspection/mutation corresponding to Java `getProcessorTable()`. Unsupported and overload codes follow the matching Java response family. RPC hooks (with identity suppression, optional Java-`equals`-style equality keys, snapshot inspection, lock-protected live-list mutation, identity/equality-key removal and explicit clear-all) and a composable request pipeline (`pipe_request_pipeline` executes the newly supplied source stage before the existing pipeline) are available; the pipeline receives the owned request and may return a typed abort (response code/remark) or failure (SYSTEM_ERROR). Existing infallible RPC hooks remain source-compatible; new fallible hook methods can abort with a response code/remark or map failures to SYSTEM_ERROR inbound / `TransportError::RpcHook` outbound; panics are not swallowed on outbound paths and propagate as Java does, while inbound processing catches them at the request-task boundary; after hooks run even when the processor returns no response, with optional response context. Outbound before hooks run after connection establishment but before async admission (as in Java's `invokeImpl` ordering), and GO_AWAY retry suppresses duplicate hooks. This is not Netty `ChannelHandlerContext` parity; typed abort and SYSTEM_ERROR outcomes are supported, but Java exception remark formatting remains different. Differences in Java executor/thread identity, rejection exception representation, and ChannelWrapper scheduling are explicitly documented as accepted runtime/framework boundaries; request-generation replacement and retry behavior are covered by the named GO_AWAY tests.
- TLS and plain TCP are explicit modes. `TransportMode::from_java_properties` maps Java `tls.enable` and enforcing-mode defaults; `TlsConfig` models Java client `tls.test.mode.enable` (default true) and `tls.client.authServer` (default false): test mode or disabled auth selects a trust-all server verifier; set both to test mode false/auth server true for chain and hostname verification. Verified mode preserves DNS for SNI, accepts caller-provided CA PEM and optional client certificate/key PEM, loads native trust roots absent a custom CA, and shares the connect deadline with handshake. Java TLS properties/config files load into Rust client configuration; the file is reread immediately before each new `RemotingClient` builds its TLS connector, while existing clients retain their settings. Process-wide `register_decryption_strategy` provides the Java `TlsHelper.DecryptionStrategy` replacement point. Java shares mutable TLS settings process-wide; each Rust `TlsConfig` source retains its own explicit property map.
- Async callback invoke acquires the connection, executes outbound before hooks, then reserves Java-sized semaphore admission within its deadline and runs callbacks through a configurable worker queue or a caller-supplied `CallbackExecutor` corresponding to Java `setCallbackExecutor`/`getCallbackExecutor`; caller-executor rejection runs the callback inline. The owned callback queue is unbounded, matching Java's public executor backlog. When `disable_callback_executor` is set, a custom executor is ignored and callbacks run inline; this remains different from Java's selected Netty event-loop/caller thread. After a channel is established, terminal outcomes call `operation_complete` before `operation_succeed`/`operation_fail`, matching the public Java `invokeAsyncImpl` callback chain; initial connection/TLS setup failures call fail only. An additional context callback exposes the invoke request (the reconstructed retry request after GO_AWAY), optional response/error, send status (Java's public async wrapper exposes the default-true `ResponseFuture.sendRequestOK` on exceptional completion, including internal send failure), timeout flag and elapsed duration. Async pending-response expiry uses Java's +1 second scan grace. Named transport tests cover callback timeout completion and metadata; exact Java exception classes/text remain documented language-level differences. SOCKS5 supports no-auth and username/password handshakes and shares the connect deadline. Configured TCP and SOCKS5 TCP send/receive buffer sizes are applied with socket-level options; write high/low watermarks track queued outbound bytes with hysteresis, while pooled allocator configuration enables a bounded per-connection frame-buffer pool (maximum four returned buffers), not Netty's allocator/thread-cache lifecycle. `disable_netty_worker_group` routes inbound processing directly on the connection task instead of queued processor workers; this approximates Java's handler-executor selection but not Netty event-loop identity or scheduling. Idle connections are closed by the owned scheduler. `channel_not_active_interval` is retained as the Java config field but does not trigger an automatic scan: pinned Java `scanChannelTablesOfNameServer()` has no call site, and its NameServer last-response check is therefore not active in the observed client control flow. `GO_AWAY` retries once under the original deadline when enabled, reconstructing a fresh request with Java defaults and preserving code/ext fields/body; hooks are not rerun. Peer/channel-close completion maps to `TransportError::SendRequest` with remote address and no cause, following Java `requestFail`; terminal `GO_AWAY` maps to the same category with a cause. Wrapper identity and reconnect edge behavior still need source-mapped tests. NameServer APIs track configured/available lists, select a round-robin address, fail over across addresses after connection failures, and scan connect availability on the configured interval. A successful response marks an address available only while that same connection generation remains current; socket close clears its chosen/available state. Java's randomized list update, exact wrapper recovery and scan-executor semantics are not fully reproduced. Availability entries for removed addresses remain observable until the next scan prunes them, matching Java's `scanAvailableNameSrv` cleanup timing. Rust rechecks configured-list membership and connection generation before applying an asynchronous probe result, preventing a removed address or stale generation from overwriting current state; Java's per-address executor and wrapper lifecycle differ. Java's protected `scanChannelTablesOfNameServer()` is not called by the pinned client source and is not treated as an active scheduled control flow. Shutdown rejects new calls, signals processors and timers, closes sockets, completes pending calls, and joins client-owned tasks. Repeated calls share one shutdown completion. The explicit `start()` transition launches inbound, callback, channel-event and timer workers on the caller's active Tokio runtime; construction starts none of these workers. User disposition accepts Tokio worker/thread identity, scheduling/polling, shutdown/drain and executor-lifecycle differences as Rust-native behavior; address-only channel-event callbacks are accepted and no Netty `Channel` handle is fabricated. These decisions do not imply Java executor or event lifecycle parity. Error subclass/cause/remark differences remain pending item-by-item disposition in `PHASE_3_REMOTING_INVENTORY.md`.

Callback metadata and +1-second async timeout grace are covered; Rust typed errors and exception-text differences are documented in the compatibility inventory. |
| `NettyRemotingAbstract.invoke0`, `processResponseCommand`, `scanResponseTable`; `ResponseFuture` | `PendingEntry`, `PendingGuard`, `timeout_scheduler` | Implemented and tested: core correlation, timeout and cancellation ownership; async callback path uses +1-second grace and exposes callback metadata. Tokio timer precision and typed error representation are documented differences. |
| `ChannelWrapper`, `getAndCreateChannel*`, `closeChannel`, `SocksProxyConfig`, channel events, NameServer methods | internal `Address`, `SocksProxyConfig`, `ChannelEventListener`, connection generations, `is_channel_writable`, `is_address_reachable`, `close_channels` | Implemented and tested: SOCKS5, idle closure/events and basic NameServer list/scan/selection/failover; reachability uses async connect and writability reflects unbounded outbound queued-byte watermarks (Netty defaults 64 KiB high / 32 KiB low), not Netty event-loop accounting; accepted differences include Java event executor lifecycle/overload behavior and Netty writability accounting. Java admits at most 10001 queued channel events; Rust uses the same bounded capacity and drops excess events, while worker lifecycle, polling, shutdown/drain and thread semantics differ. |
| `NettyRemotingAbstract.processRequestCommand`, processor table and `getProcessorTable()`, RPC hooks/pipeline, `GO_AWAY` | `RequestProcessor`, `ProcessorRegistration` / `with_processor_table`, `RpcHook`, `RequestPipeline`, `TransportError::SendRequest` | Implemented and tested: hooks/pipeline/rejection, default processor fallback and one GO_AWAY retry; retry request reconstruction is covered by `p3_go_away_retries_once_on_a_new_connection`. | `NettyRemotingClient` TLS configuration and `TlsHelper` | `TransportMode::{Tls,from_java_properties}` and `TlsConfig` | Implemented and tested: client TLS selection, property-file reload before each new client TLS-context construction, and process-wide decryptor registration. ## Verification

Scripted TCP/TLS loopback tests in `crates/rocketmq-classic-remoting/tests/transport.rs` plus private unit race tests cover automated subsets of P3-V01/V02/V03/U01, including stale generations, opaque wrap, cancellation/timeout/response/shutdown terminal ownership, saturation, TLS trust/hostname failures, caller callback executor routing/rejection, owned-request pipeline execution, typed abort mapping and fallible RPC-hook abort/error, outbound before-hook execution after connection establishment (including a one-way hook-before-admission ordering case), Java-style pipeline/after-hook handling on ordinary inbound before-hook failure, absent-response after-hook behavior, connect-failure channel events, and callback send-status outcomes on peer close. They are offline transport checks, not Broker behavior or final Java release parity. Earlier Phase 3 dispositions accepted the lower-level transport config snapshot, Tokio executor/scheduling/lifecycle, selected Rust-native API representations and documented Netty framework differences. Phase 18 reopens each row that affects public API/settings or observable behavior; historical acceptance labels alone do not establish parity. Core runtime config mutability follows ADR-0037. TLS properties now use process-wide retained state in Java-compatible Rust property sources, while existing RemotingClient instances keep their constructed connector; bounded frame reuse, direct inbound dispatch and queued-byte writability are Rust implementations, with observable capability matching tracked in the compatibility inventory. P3-V04 remains reserved for Phase 19. See `docs/compatibility/JAVA_5_5_1_COMPATIBILITY.md` for the matrix and gaps.
