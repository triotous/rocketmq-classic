# ADR-0014: Match pinned Fastjson scalar coercions in route DTO inputs

Status: Accepted

## Context

The Java 5.5.1 client decodes route responses into `QueueData`, `BrokerData`, `TopicRouteData`, `TopicQueueMappingInfo`, and `MessageQueue` with Fastjson 2.0.63. The Rust DTOs previously used direct Serde field decoding. That rejected several inputs Java accepts and decoded Java's primitive null defaults differently.

## Decision

Add narrow JSON deserializers in `rocketmq-classic-common::serde_fastjson` and attach them to the affected DTO fields. The tested behavior includes scalar-to-string conversion, Java primitive defaults for null, integer strings and fractions, boolean inputs, normalized numeric map keys, nullable Broker addresses, and scalar members of route filter lists. Numeric tokens retain their original text where Java's decimal narrowing depends on low bits; integer tokens outside the target range, invalid boolean strings, and null static-mapping values remain rejected.

The input helpers keep Rust DTO field types and ordinary Serde encoding unchanged. Java exception classes are not reproduced; Rust exposes Serde errors at the decode boundary. HashMap/ConcurrentHashMap iteration order and untested Fastjson grammar are not asserted equivalent.

The route JSON adapters normalize accepted unquoted numeric keys only inside map or generic-object contexts. `brokerAddrs` and `currIdMap` preserve numeric key lexemes for Java integer coercion; `filterServerTable` and `topicQueueMappingByBroker` stringify numeric keys using Java number text, including exponent formatting. Unquoted numeric bean properties remain rejected. Other nonstandard tokens remain subject to Serde rejection unless directly covered by the oracle.

For inherited `RemotingSerializable` methods, `TopicRouteData` and `TopicQueueMappingInfo` expose Java-compatible `java_to_json`, `java_encode`, `java_decode`, `java_decode_list`, and `java_from_json` adapters, plus nullable decode/list/fromJson forms. These adapters sort object properties, reproduce Fastjson2's unquoted numeric keys for `brokerAddrs` and `currIdMap`, and match the tested pretty-print form. The route API uses `TopicRouteData::java_decode_nullable` for response bodies. Numeric object keys are normalized before Serde parsing; other unquoted keys remain invalid. Native map output is deterministic, while Java HashMap/ConcurrentHashMap iteration order is unspecified.

## Evidence

At the 2026-10-09 field-shape checkpoint, `RuntimeRouteFixtures.routeDtoInputCases` invoked 287 actual inputs for `QueueData`, `MessageQueue`, `BrokerData`, `TopicQueueMappingInfo`, and nested `TopicRouteData`. The 133-case base corpus covers scalar conversions, integer-string coercions, duplicate-last fields, JSON grammar, Unicode decimal rejection, numeric map-key collisions, and list shapes. A 154-case matrix tests seven JSON value shapes (null, numeric string, integer, fraction, Boolean, array, object) against every field in the 22 `QueueData`, `BrokerData`, `TopicQueueMappingInfo`, and `TopicRouteData` properties. It found that Java Fastjson rejects an empty object for `TopicQueueMappingInfo.epoch`, while the native decoder previously converted it to zero; both the public DTO and last-wins input helper now use the object-rejecting i64 decoder. The comparison treats nested absent and explicit-null fields as the same nullable DTO value; encoding omission remains tested separately by the inherited serialization fixture. Later continuations expand the corpus to 337 cases below.

The `MessageQueue.queueId` cases cover explicit null to zero, signed integer boundaries, fractional truncation, and overflow rejection. Twelve added cases establish that route DTO `JSON.parseObject` rejects JSON5-style single quotes, comments, unquoted non-integer bean keys, trailing commas, numeric suffixes, plus malformed collection shapes; native route DTO parsing rejects the same inputs. The later numeric-key probes below establish the specific exception for unquoted signed integer keys inside `brokerAddrs` and `currIdMap`. Five further cases confirm Java rejects fullwidth and Arabic-Indic decimal strings in integer fields, queue IDs, and numeric map keys, which the native decoder also rejects. Six cases confirm Java accepts leading-plus and zero-prefixed integer, decimal, and exponent values, while three cases confirm NaN, Infinity, and hex numeric tokens reject. Eight whitespace/BOM cases show that Fastjson accepts form feed before the document, before a value, and around object punctuation, and accepts a BOM only at the document start; vertical tab, NBSP, and a BOM inside the document reject. Seven `MessageQueue.queueId` string cases show Java accepts `+2`, `002`, `-1.9`, and `1e2` as 2, 2, -1, and 100, while whitespace-padded and out-of-range values reject. Ten `TopicQueueMappingInfo.epoch` cases cover decimal/exponent and Long-boundary inputs; decimal values truncate and wrap to Java's low 64 bits, while overflowing integer tokens reject. The `currIdMap` decimal cases confirm Java's low-32-bit narrowing, including `9223372036854775807.0` to -1, `2147483648.0` to -2147483648, and `-2147483649.0` to 2147483647. Two high-precision number-to-string cases cover broker address map values and nested filter-server lists; plain decimal digits remain exact and exponent values follow Java formatting. A further boolean case establishes that Java and Rust both return false for the decimal `1.0000000000000000001`. The route parser boundary is separate from the permissive SOCKS constructor parser.
