# Phase 3 Remoting API and Configuration Inventory

Phase 5 adds `invoke_sync_with_deadline` and `invoke_name_server_sync_with_peer` as absolute-deadline representations of Java `invokeSync` overloads (ADR-0003). Existing duration and future adapters retain their behavior. Core mode regression tests distinguish synchronous wait expiry from future response-table cleanup grace; NameServer sync selection preserves one original deadline and returns the invocation's peer metadata.

Java source baseline: `rocketmq-all-5.5.1`, commit `efa1be59d6fc747ad220f036c86030f05f0419f9`. Rust paths are relative to the repository root. Tests refer to `crates/rocketmq-classic-remoting/tests/transport.rs` unless noted otherwise. This ledger is for the client-side remoting scope only; Netty implementation details that have no Tokio semantic equivalent are recorded as differences, not parity.

Status meanings: `MAPPED` means a Rust API or internal behavior and named local test exists; `PARTIAL` means behavior differs or not all Java branches are covered; `NOT MAPPED` means no Rust equivalent. No row claims live Broker validation.

## Explicit acceptance decisions

This inventory records earlier Phase 3 decisions that `ClientConfig` is a fixed construction-time snapshot and that Tokio executor, callback scheduling, ownership, and lifecycle may differ from Java. The current Phase 18 parity contract supersedes any blanket acceptance of unmatched Rust-only public APIs or settings: public capabilities and settings must correspond to Java 5.5.1, while Rust may use idiomatic Rust types and components to express them. The historical decisions do not close rows that have not been rechecked against that contract. P3-V04 remains deferred to Phase 19.

Earlier Phase 3 notes classified Rust queued-byte writability/watermark accounting versus Netty outbound-buffer writability, NameServer scan deferral versus Java queue rejection and related scheduling/list/wrapper differences, and historical gaps around APIs carried by Netty/JVM objects such as `Channel`, `ChannelHandlerContext`, `ResponseFuture`, and `ChannelWrapper`. Rust now represents callback/future channel capabilities through `ResponseFuture` and identity-preserving `ChannelHandle` values, and inbound processors/pipeline stages receive a shared `RequestContext` with that channel identity, peer address, close, and write capability; it does not fabricate Netty objects or expose raw Tokio sockets. These historical classifications do not by themselves establish equivalent public capabilities or observable behavior under the current Phase 18 contract. P18-V01 must verify each Java source path and Rust representation; existing tests and source mappings remain evidence requirements.

The user also decided that support for TLS encryption algorithms or key sizes unavailable in the selected RustCrypto/rustls dependencies is not mandatory. This applies only to those provider/library capability limits; it does not waive TLS modes, trust/hostname validation, Java fixtures currently supported by the dependencies, or Phase 19 live-validation requirements.

Additional user decisions: signed negative Java time-configuration values must not be rejected merely because Rust `Duration` cannot represent them; their runtime behavior must be determined from the Java/Netty source and mapped. Rust's bounded per-connection frame `Vec` reuse is accepted as a Rust-native alternative to reproducing Netty pooled-allocator internals. Rust hook `equality_key` and lock-scoped collection access semantics are accepted instead of arbitrary Java `equals()` and unsynchronized live collection references. The latter two decisions accept only the representation/allocator differences, not missing transport behavior or unrelated Rust-only public capabilities.

The table below records Rust-shaped surfaces that lacked a distinct Java public declaration in the earlier inventory. Retain a surface only when it expresses an existing Java public capability or an agreed Rust-native representation of that capability; a Rust-only capability or setting remains a P18-V01 blocker. This is not a blanket waiver for missing behavior. Java `ChannelWrapper` reconnect/replacement behavior has been reviewed for request-generation paths: a GO_AWAY on the wrapper's current channel may replace it and trigger retry; once the wrapper has switched, later GO_AWAY responses arriving on that old channel also retry through the wrapper's current channel. Thus multiple pending requests on one old generation can share the same replacement, while their original requests may still complete if the peer responds normally. `ChannelWrapper.reconnect` uses `tryLock`, so a callback that races before the current-channel swap can fail if it cannot acquire the lock; the deterministic regression covers a later response after the swap and does not claim every lock-contention interleaving retries. A GO_AWAY response processed after the original socket-close cleanup can still mark the old generation as retired and retry if no replacement is cached; a concurrently cached replacement is not evicted. Rust covers this with `p3_go_away_retries_once_on_a_new_connection`, `p3_go_away_replacement_keeps_other_old_connection_requests_alive`, and `p3_all_requests_on_retired_connection_retry_once_on_shared_replacement`. Explicit address close and shutdown close both current and retired generations. Replacement/close interleavings remain subject to the source-backed coverage and tests listed in this inventory; they are not assumed exhaustive.

## Rust public API additions and Rust-to-Java mapping

The following Rust APIs are Rust-shaped forms or extensions without a one-to-one Java declaration. They are recorded here to make the mapping bidirectional rather than treating every Rust name as a Java method. Each surface is classified below as an adapter for existing Java behavior or an explicit Rust-native result/ownership contract; a similar name alone is not evidence of equivalence. Construction snapshots `ClientConfig`: semaphore capacities and SOCKS JSON routes are consumed while constructing `RemotingClient`; processor/callback/event workers and periodic schedulers are created at `start()`; socket options, watermarks, TLS connector, and idle timeout are applied when each connection is created; request deadlines and current listener/processor/hook registrations are consulted per operation. Mutating the caller's config after construction is impossible because it is moved into the client. Java's `NettyClientConfig` remains mutable, but `NettyRemotingClient` captures some values at construction (semaphores, callback/public executors, SOCKS routes, TLS context) and reads other values from the retained config at `start()`, connection bootstrap, or each operation. This inventory historically accepted Rust's fixed construction-time snapshot. Live adapters now cover the Remoting values Java reads from retained config at start, per proxy-CIDR first use, per channel, or per operation; settings captured at construction/start are identified by row. P18-V01 still must complete the source/API, overload/input/error/control-flow, inherited API, and Rust reverse-export reconciliation, including the disposition of Rust-native ownership and runtime differences.

### Rust-only public API surface audit

This audit lists API capabilities without a distinct Java public method/setting. “Java semantic counterpart” means a Rust-shaped interface for an existing Java capability, not a blanket no-additions waiver. An extension is not accepted merely because it is idiomatic: it must map to an existing Java capability or to an explicitly agreed Rust-native contract, otherwise it remains an acceptance blocker.

Custom-header validation maps `CommandHeader::check_fields` and the checked decode path to Java `RemotingCommand.decodeCommandCustomHeader` and `CommandCustomHeader.checkFields`. The invoked `commandCustomHeaders.checkFields` fixture covers create-topic filter values, end-transaction and transaction-response states, and a custom header's valid, negative, and missing values. The separate `end-transaction-header-decode-modes.json` fixture invokes Java with both mode hints and records per-field conversion/missing-field handling before final commit-state validation. Rust reports typed `ProtocolError` values; Java exception text and classes are not claimed as identical. These named cases do not close the broad P18-V01 source/API/input/error/flow audit.

`decodeCommandCustomHeaderDirectly(headerClass, useFastEncode)` now maps the mode to `CommandHeader::decode_fields_with_mode`. The invoked Java 5.5.1 Pull header fixture covers fast versus reflective decoding for missing fields, valid fields, and invalid `queueId`, `maxMsgBytes`, and `requestSource`; Rust preserves absent nullable values, matches fast-mode numeric rejection, and skips individual invalid conversions in reflection mode. The inherited `lo` field is included. Other header implementations still use the default mode adapter; this Pull-specific result does not close the broad P18-V01 decoder/API audit.

P18-V01 nullable numeric reflection follow-up (2026-10-18, code commit `1a4924a3`): `ConsumerSendMsgBackRequestHeader`, `ResetOffsetRequestHeader`, `ConsumeMessageDirectlyResultRequestHeader`, `ReplyMessageRequestHeader`, and `SendMessageRequestHeaderV1` do not implement `FastCodesHeader`, so both `useFastEncode` hints use Java's per-field reflection decoder. Rust now keeps nullable numeric fields unset on malformed/overflow input while continuing to decode sibling fields; it parses Java BMP decimal digits such as Arabic-Indic digits, and retains `ResetOffsetRequestHeader.queueId`'s initial `-1` when reflection conversion fails. The invoked fixture compares both hints and these cases; SHA-256 `f4bc4d7c18fc82a43a07f45f052f710644dcd950f7a5c5c0a0333a25435580f5`. This closes only these named field paths; other primitive/required numeric header branches and the broad P18-V01 audit remain open.

### Exception, cause, and remark parity requiring item-by-item disposition

Java exposes checked exception subclasses, public message/cause constructors, and nested `Throwable` causes; Rust uses a closed `TransportError` enum with `ErrorSource` wrapping the standard `Error::source()` chain. `ErrorSource::new` and `with_context` preserve typed and nested causes, `message` supplies a message-only cause, and `downcast_ref` inspects the chain. Timeout/connect/TLS source factories are crate-internal implementation helpers; callers inspect or construct public variants directly. The error-class/cause/remark disposition requested by the plan is applied below: preserve original typed causes where available, retain contextual timeout information, and accept Rust-native callback and event error surfaces. These decisions do not claim Java exception hierarchy or exact remark parity. Derived Rust error equality is structural/value-based and is not used by transport flow decisions; Java `Throwable` inherits identity equality.

|---|---|---|

Java `NettyRemotingClient` commonly constructs this exception with null cause, so Rust's richer source diagnostic is an intentional addition, not asserted as Java cause parity. |
| Sync write / response failure: `RemotingSendRequestException("send request to <addr> failed", cause)`; async `requestFail` sets send status and callback later constructs the exception with `getCause()` (usually null) | `SendRequest { remote_addr, cause: Some(ErrorSource) }` for typed socket-write failures; the original source chain is retained. ## Inventory conclusion

The scoped Java public interface, concrete client surface and overloads (including protected `doConnect`/`getHostAndPort`, nested handler/wrapper types, and channel-close overloads), inherited `NettyRemotingAbstract` public/protected APIs, callback/response-future, processor, event, all `NettyClientConfig` settings/accessors, relevant `NettySystemConfig` properties, TLS controls, Rust public declarations and configuration validation/defaults are enumerated against current Rust APIs and named scripted/unit tests in both directions. GO_AWAY source review now covers wrapper replacement without eagerly closing the old channel, generation-scoped retry, concurrent old-channel pending requests, multiple GO_AWAY responses on one retired generation, stale close behavior and replacement lifecycle; the old connection is retained until closure, explicit address close or client shutdown. Explicit close and shutdown both drain retired connections; request/replacement/close interleavings listed in this inventory have named regression coverage. The Rust-only public API table names the extensions found in the scoped remoting client surface; the public event-generation field and `ChannelHandle::generation()` getter, along with the public address parser, have been removed, and the private Java channel-future helper has no public Rust counterpart. Callback result metadata, executor/error traits, lock-scoped collection accessors and explicit TLS property/decryption adapters are Rust ownership/type representations of existing Java capabilities, not new wire or transport features; Java Netty/JVM types and global state are not fabricated. Rust oneway returns only call-boundary errors and schedules a client-owned operation; Java also discards post-return transport outcomes. This scoped behavior is reconciled and no longer an open difference by itself. Inbound response writes follow Java's no-fixed-deadline behavior and terminate on connection shutdown. The config rows identify Java property seeds versus explicit Rust config and capture whether each setting is read at construction, start, proxy-CIDR first use, per-channel creation or per operation; live adapters cover settings Java reads from its retained mutable config, and construction/start snapshots are called out by row. These Remoting setting rows are now reconciled, but they do not close the broader P18-V01 Java/Rust API, overload/input/error/control-flow and reverse-export audit. `getNameServerAddressList()` preserves Java's null-versus-list distinction as `Option<Vec<String>>`; `with_name_server_address_list` provides lock-scoped access to mutate the live backing list, and empty updates still leave the prior value unchanged. Rust exposes lock-protected `with_rpc_hooks` and `with_processor_table` access to the live collections as well as hook snapshot inspection, matching mutable inspection while preventing unsynchronized aliases. Source review covers outbound hook-before-admission ordering for future/callback and oneway paths; Java `invokeSync` runs outbound hooks through virtual `invokeImpl` dispatch before async semaphore admission, now covered by `p3_sync_invoke_obeys_async_admission_and_runs_hooks_first`; sync admission-time timeout is surfaced through Java's send-request wrapper and closes the acquired channel (`p3_sync_admission_failure_maps_to_send_request_and_closes_socket`), while oneway hook timing has dedicated test `p3_outbound_rpc_hook_runs_before_oneway_admission_wait`. Public callback send status follows Java's wrapper-created default `ResponseFuture` on exceptional completion (true), even if the internal response future marked send failure; covered by scripted peer tests. Callback executor access now exposes the default effective executor and resetting the custom executor restores it, while Java executor ownership/lifecycle differences remain narrowly documented. It also covers Java inbound before-hook/pipeline/processor/after-hook branches represented by Rust typed outcomes, callback failure ordering and GO_AWAY retry branches. Java `channelNotActiveInterval` is inert in the pinned client's observed scheduled flow because its only use is a protected method without a call site; Rust no longer imposes an extra automatic close policy from that setting. Historical `PARTIAL`, `NOT MAPPED`, `NOT EQUIVALENT` and `ACCEPTED DIFFERENCE` labels retain their row-level detail, but do not by themselves satisfy the current Phase 18 contract. P18-V01 must verify that each public capability and setting maps to Java 5.5.1 and that observable behavior is equivalent.
