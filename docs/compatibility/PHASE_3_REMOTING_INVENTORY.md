# Phase 3 Remoting API and Configuration Inventory

Java source baseline: `rocketmq-all-5.5.1`, commit `efa1be59d6fc747ad220f036c86030f05f0419f9`. Rust paths are relative to the repository root. Tests refer to `crates/rocketmq-classic-remoting/tests/transport.rs` unless noted otherwise. This ledger is for the client-side remoting scope only; Netty implementation details that have no Tokio semantic equivalent are recorded as differences, not parity.

Status meanings: `MAPPED` means a Rust API or internal behavior and named local test exists; `PARTIAL` means behavior differs or not all Java branches are covered; `NOT MAPPED` means no Rust equivalent. No row claims live Broker validation.

A callback already executing in `spawn_blocking` cannot be forcibly stopped, so the bound guarantees `shutdown().await` returns, not that arbitrary user code has terminated. Repeated calls are idempotent. Covered by `shutdown_is_idempotent_and_new_calls_are_rejected`, `shutdown_bounds_wait_for_a_blocking_callback`, `p3_shutdown_drains_callback_from_pending_invoke`, and shutdown portions of `p3_u01_raw_route_deadline_shutdown_and_address_parsing` / TLS tests. |

## Inventory conclusion

The scoped Java public interface, concrete client surface and overloads (including protected `doConnect`/`getHostAndPort`, nested handler/wrapper types, and channel-close overloads), inherited `NettyRemotingAbstract` public/protected APIs, callback/response-future, processor, event, all `NettyClientConfig` settings/accessors, relevant `NettySystemConfig` properties, TLS controls, Rust public declarations and configuration validation/defaults are enumerated against current Rust APIs and named scripted/unit tests in both directions. `getNameServerAddressList()` now preserves Java's null-versus-list distinction as `Option<Vec<String>>`; empty updates still leave the prior value unchanged. Rust exposes lock-protected `with_rpc_hooks` and `with_processor_table` access to the live collections as well as hook snapshot inspection, matching mutable inspection while preventing unsynchronized aliases. Source review covers outbound hook-before-admission ordering for future/callback and oneway paths; Java `invokeSync` runs outbound hooks through virtual `invokeImpl` dispatch before async semaphore admission, now covered by `p3_sync_invoke_obeys_async_admission_and_runs_hooks_first`; sync admission-time timeout is surfaced through Java's send-request wrapper and closes the acquired channel (`p3_sync_admission_failure_maps_to_send_request_and_closes_socket`), while oneway hook timing has dedicated test `p3_outbound_rpc_hook_runs_before_oneway_admission_wait`. Public callback send status follows Java's wrapper-created default `ResponseFuture` on exceptional completion (true), even if the internal response future marked send failure; covered by scripted peer tests. Callback executor access now exposes the default effective executor and resetting the custom executor restores it, while Java executor ownership/lifecycle semantics remain partial. It also covers Java inbound before-hook/pipeline/processor/after-hook branches represented by Rust typed outcomes, callback failure ordering and GO_AWAY retry branches. Java `channelNotActiveInterval` is inert in the pinned client's observed scheduled flow because its only use is a protected method without a call site; Rust no longer imposes an extra automatic close policy from that setting. The scoped inventory is closed in both directions, but that is inventory completeness rather than semantic parity; rows marked `PARTIAL`, `NOT MAPPED` or `NOT EQUIVALENT` remain acceptance blockers. Java `getRPCHook()` and `getProcessorTable()` mutable-inspection APIs now have Rust lock-protected live collection accessors; channel-object close overloads and Netty context/framework entry points remain absent because their framework types have no Rust-native public counterpart. TLS system/config-file keys load to per-client snapshots, and a per-client decryptor can be supplied; Java's global mutable reload-at-each-context-build lifecycle is explicitly accepted as a Rust per-client isolation exception (not a RocketMQ wire/API capability), while built-in PBES1/PBES2 encrypted-key decryption now covers the Java fixture and supported RustCrypto formats (unsupported algorithms remain a known limitation). Java's insecure trust-all test/auth modes are explicitly mapped; verified mode remains selectable. `P3-V04` remains `PENDING_PHASE_19`; offline tests and this ledger are not Broker evidence.
