# Phase 3 Remoting API and Configuration Inventory

Java source baseline: `rocketmq-all-5.5.1`, commit `efa1be59d6fc747ad220f036c86030f05f0419f9`. Rust paths are relative to the repository root. Tests refer to `crates/rocketmq-classic-remoting/tests/transport.rs` unless noted otherwise. This ledger is for the client-side remoting scope only; Netty implementation details that have no Tokio semantic equivalent are recorded as differences, not parity.

Status meanings: `MAPPED` means a Rust API or internal behavior and named local test exists; `PARTIAL` means behavior differs or not all Java branches are covered; `NOT MAPPED` means no Rust equivalent. No row claims live Broker validation.

## Public client/service methods

| Java declaration/source | Rust mapping | Coverage / status |
|---|---|---|
| `RemotingService.start()` | Construction starts Tokio-owned tasks in `RemotingClient::with_config`; there is no separate public start call | `PARTIAL`: lifecycle ownership is different; constructor requires a runtime and has no explicit start transition. |
| `RemotingService.shutdown()` | `RemotingClient::shutdown()` | `MAPPED`: client unit `shutdown_is_idempotent_and_new_calls_are_rejected` and shutdown portions of `p3_u01_raw_route_deadline_shutdown_and_address_parsing`, TLS test. |
| `RemotingService.registerRPCHook(RPCHook)` / `clearRPCHook()` | `add_rpc_hook` / `clear_rpc_hooks` | `PARTIAL`: duplicate `Arc` registrations are ignored by pointer identity; Java uses `List.contains`/`equals`, so custom equality semantics differ. | `RemotingService.setRequestPipeline(RequestPipeline)` | `set_request_pipeline(Option<Arc<dyn RequestPipeline>>)` / `pipe_request_pipeline(Arc<dyn RequestPipeline>)` | `PARTIAL`: supports replacement and Java `RequestPipeline.pipe` order (new source stage, then existing stage); `None` still clears directly rather than representing a Java pipeline. | `RemotingClient.updateNameServerAddressList(List<String>)` | `update_name_server_address_list(Vec<String>)` | `PARTIAL`: non-empty replacement and chosen-channel cleanup exist; changed lists are shuffled (using Rust RNG), and duplicates are retained. Rust now retains removed addresses in the exposed available set until the next scan prunes them, matching Java's stale-key cleanup timing (`p3_nameserver_update_prunes_availability_on_next_scan`); Java also shuffles the caller's list in place while Rust owns its input vector. `p3_nameserver_update_shuffles_changed_lists_and_preserves_duplicates` covers multiset retention and the no-change membership path, but does not assert random order. `p3_nameserver_list_selection_and_availability_tracking`, `p3_nameserver_recovers_selection_after_chosen_channel_closes`. |
| `getNameServerAddressList()` | `get_name_server_address_list()` | `PARTIAL`: Rust returns an empty `Vec` when unconfigured while Java may return `null`; same NameServer tests. |
| Private Java `getAndCreateChannel(String)` / `getAndCreateChannelAsync(String)` helpers | Internal `ClientInner::connection` | `PARTIAL`: Rust has async deadline-bound acquire/reuse with per-address single-flight; Java returns Netty `Channel`/`ChannelFuture` and uses its channel-table lock and wrapper lifecycle. | `getAvailableNameSrvList()` | `get_available_name_srv_list()` | `PARTIAL`: Rust returns an available-set snapshot, which can temporarily include a just-removed address until the next scan just like Java; Java returns keys from a concurrent map with unspecified order. NameServer availability tests include `p3_nameserver_update_prunes_availability_on_next_scan`. |
| `invokeSync(String, RemotingCommand, long)` | `invoke(addr, command, deadline)` and `invoke_sync(addr, command, Duration)` | `PARTIAL`: async Rust future rather than Java blocking API/checked exception types. Only `invoke_sync` applies Java's configurable timeout socket-close heuristic; future-based `invoke` and callback `invoke_async` do not close the socket on response timeout. Covered by `p3_v01_parallel_responses_and_opaque_lifecycle`, `p3_u01_raw_route_deadline_shutdown_and_address_parsing`, `p3_u01_inflight_invoke_times_out_when_peer_does_not_reply`, `p3_go_away_response_uses_explicit_transport_error`. |
| `invokeAsync(String, RemotingCommand, long, InvokeCallback)` | `invoke_async(addr, command, deadline, callback)` | `PARTIAL`: connection acquisition precedes semaphore admission as in Java's async path; callback metadata/order and admission timeout exist. Java callback throwable taxonomy, `ResponseFuture` contract and races are not identical. Covered by `p3_async_connection_is_acquired_before_admission_wait`, callback metadata/grace, expiry, admission and custom-executor tests listed below. |
| `invokeOneway(String, RemotingCommand, long)` | `invoke_oneway(addr, command, deadline)` | `PARTIAL`: Rust schedules connection acquisition, hook, semaphore admission and write on an owned task, then returns without waiting. Java initiates/obtains its channel future synchronously before listener registration and return; Rust task polling may begin after return. Post-return failures are intentionally unobservable; deadline-bound admission/write, bounded local queue and Java semaphore exception behavior differ. Covered by `p3_oneway_returns_after_scheduling_before_peer_receives_frame` and `p3_u01_raw_route_deadline_shutdown_and_address_parsing`. |
| default `invoke(String, RemotingCommand, long)` returning `CompletableFuture<RemotingCommand>` | `async fn invoke(&self, addr, command, deadline) -> Result<RemotingCommand, TransportError>` | `PARTIAL`: this is the Rust-native future-returning equivalent and does not require callback adaptation; deadline is absolute `Instant` rather than relative milliseconds and Java exception classes become `TransportError`. Covered by `p3_v01_parallel_responses_and_opaque_lifecycle`, `p3_u01_raw_route_deadline_shutdown_and_address_parsing`, and `p3_go_away_response_uses_explicit_transport_error`. |
| `registerProcessor(int, NettyRequestProcessor, ExecutorService)` | `register_processor_with_executor(code, processor, Option<Arc<dyn RequestExecutor>>)` | `PARTIAL`: per-code executor and rejection covered by `p3_processor_specific_and_default_executors_route_or_reject_tasks`; Java executor lifecycle and `ChannelHandlerContext` unavailable. |
| `setCallbackExecutor(ExecutorService)` / `getCallbackExecutor()` | `set_callback_executor` / `get_callback_executor` | `PARTIAL`: custom setter/getter identity and clear are exercised by `p3_caller_callback_executor_routes_callbacks_to_owned_executor`; executor routing/rejection are exercised by that test and `p3_callback_executor_rejection_runs_callback_inline`. Rust getter returns only a caller-supplied executor; Java returns the effective public executor (or `null` when disabled), and Rust does not expose its internal default worker pool as an executor object. `Arc` trait-object ownership/lifecycle also differs from Java `ExecutorService`. With `disable_callback_executor`, Rust discards a custom executor assignment, returns `None`, and dispatches inline, matching Java's disabled-executor selection; the config/setter interaction is asserted in `p3_controls_validate_defaults_hooks_callback_and_channel_events`. |
| `isChannelWritable(String)` | `is_channel_writable(&str)` | `PARTIAL`: queue capacity or Rust queued-byte hysteresis, not Netty channel writability. Covered by `p3_channel_management_matches_java_unknown_writable_and_explicit_close_contract`. |
| `isAddressReachable(String)` | `is_address_reachable(&str, deadline)` | `PARTIAL`: Rust operation is async and requires explicit deadline. Same channel management test. |
| `closeChannels(List<String>)` | `close_channels(&[String])` | `PARTIAL`: matching pull requests are interrupted and cached channels closed; error representation differs. Covered by `p3_close_channels_interrupts_pending_pull_requests_only`. |
| concrete `NettyRemotingClient.closeChannel(String, Channel)` / `closeChannel(Channel)` | `close_channels(&[String])` | `PARTIAL`: Rust closes cached connection(s) by address and has no public channel-object or channel-identity overload; Java protects wrapper replacement while closing a specific channel. Covered indirectly by stale-generation and explicit-close tests. |
| `getChannelEventListener()` and constructor injection | `set_channel_event_listener` / `get_channel_event_listener` | `PARTIAL`: Java listener is constructor-injected and immutable; Rust is mutable at runtime. Callbacks omit the Java `Channel` argument and worker lifecycle/order differ. Getter identity/clear plus basic delivery are covered by `p3_hooks_and_channel_connect_event_follow_successful_exchange`; config/event basics by `p3_controls_validate_defaults_hooks_callback_and_channel_events`. |
| inherited `NettyRemotingAbstract.getRPCHook()` / `getProcessorTable()` | No public getter; Rust exposes hook and processor registration only | `NOT MAPPED`: Java returns mutable internal collections/maps; Rust intentionally does not expose mutable internal state. Mutability and returned collection identity have no safe direct equivalent. |
| protected `scanChannelTablesOfNameServer()` / private `scanAvailableNameSrv()` | Internal `timeout_scheduler` / `scan_available_name_servers` | `PARTIAL`: initial scan and connect-timeout cadence are modeled; Rust probes configured addresses concurrently and removes availability for removed addresses. Java schedules per-address work on its scan executor and uses channel-wrapper activity timestamps, whereas Rust owns Tokio JoinSet probes and scans NameServer stale responses in the timeout scheduler. Cleanup, overlap races and wrapper selection still differ; not public Rust API. | inherited public `putNettyEvent`, `processMessageReceived`, `processRequestCommand`, `processResponseCommand`, `doAfterRpcHooks`, static `writeResponse`, `scanResponseTable`, invoke `*Impl`, and `getProcessorTable` framework methods | Internal inbound dispatcher, response matcher, hook runner, writer, timeout scheduler and processor registry | `PARTIAL`: Java methods expose Netty `ChannelHandlerContext`/`Channel`, mutable processor state or Java response-table lifecycle. Rust equivalents are private and do not expose framework internals; behavior is covered by named inbound, callback, hook and lifecycle tests. `getRPCHook`/`getProcessorTable` inspection is explicitly not mapped. |

## Callback and response-future surface

| Java source API | Rust mapping | Coverage / status |
|---|---|---|
| `InvokeCallback.operationComplete(ResponseFuture)` | `InvokeCallback::operation_complete(&Result<...>)`; overridable `operation_complete_with_context(&InvokeCallbackResult)` | `PARTIAL`: result/context abstraction differs from mutable Java `ResponseFuture`. `NettyRemotingClient.InvokeCallbackWrapper` forwards `operationComplete` to the application, while the public `NettyRemotingAbstract.invokeAsyncImpl` chain invokes application `operationComplete` in `whenComplete` before its subsequent `thenAccept`/`exceptionally` calls `operationSucceed`/`operationFail`; Rust follows this public callback order after a channel is established. Java's initial channel-creation/setup failure invokes only `operationFail`; Rust skips complete only if no connection was ever established. If GO_AWAY retry connection setup fails after the first channel existed, Java's `invokeAsyncImpl` chain invokes `operationComplete` before `operationFail`; Rust preserves that distinct order, covered by `p3_async_go_away_retry_connect_failure_completes_before_failure`. |
| `InvokeCallback.operationSucceed(RemotingCommand)` / `operationFail(Throwable)` | `operation_succeed(&RemotingCommand)` / `operation_fail(&TransportError)` | `PARTIAL`: Rust error enum does not preserve every Java exception class/cause. |
| `ResponseFuture.executeInvokeCallback`, `interrupt`, `release`, `isTimeout`, `waitResponse`, getters/setters for begin time/send status/timeout/callback/cause/response/opaque/request/channel/interrupted | No public `ResponseFuture`; private `PendingEntry`, `PendingGuard`, `InvokeCallbackResult` | `PARTIAL`: ownership and immutability differ; Java channel/cause/release contract is not exposed. Tests: `p3_async_callback_contains_response_future_metadata_and_timeout_grace`, `p3_expired_async_callback_retains_request_and_timeout_metadata`, `p3_async_callback_completes_on_deadline_failure`, `p3_async_admission_timeout_completes_through_callback`, `p3_async_connect_failure_calls_fail_without_complete`, `p3_async_go_away_retry_connect_failure_completes_before_failure`, `p3_callback_executor_rejection_runs_callback_inline`. |
| `NettyRemotingAbstract.scanResponseTable()` timeout completion | Owned Tokio `timeout_scheduler`, pending deadline checks and async callback scan grace | `PARTIAL`: no Java callback-executor scan semantics or identical timeout race. Covered by callback metadata/grace and core pending-race tests. |
