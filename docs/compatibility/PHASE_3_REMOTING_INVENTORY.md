# Phase 3 Remoting API and Configuration Inventory

Phase 5 adds `invoke_sync_with_deadline` and `invoke_name_server_sync_with_peer` as absolute-deadline representations of Java `invokeSync` overloads (ADR-0003). Existing duration and future adapters retain their behavior. Core mode regression tests distinguish synchronous wait expiry from future response-table cleanup grace; NameServer sync selection preserves one original deadline and returns the invocation's peer metadata.

Java source baseline: `rocketmq-all-5.5.1`, commit `efa1be59d6fc747ad220f036c86030f05f0419f9`. Rust paths are relative to the repository root. Tests refer to `crates/rocketmq-classic-remoting/tests/transport.rs` unless noted otherwise. This ledger is for the client-side remoting scope only; Netty implementation details that have no Tokio semantic equivalent are recorded as differences, not parity.

Status meanings: `MAPPED` means a Rust API or internal behavior and named local test exists; `PARTIAL` means behavior differs or not all Java branches are covered; `NOT MAPPED` means no Rust equivalent. No row claims live Broker validation.

## Explicit acceptance decisions

This inventory records earlier Phase 3 decisions that `ClientConfig` is a fixed construction-time snapshot and that Tokio executor, callback scheduling, ownership, and lifecycle may differ from Java. The current Phase 18 parity contract supersedes any blanket acceptance of unmatched Rust-only public APIs or settings: public capabilities and settings must correspond to Java 5.5.1, while Rust may use idiomatic Rust types and components to express them. The historical decisions do not close rows that have not been rechecked against that contract. P3-V04 remains deferred to Phase 19.

Earlier Phase 3 notes classified Rust queued-byte writability/watermark accounting versus Netty outbound-buffer writability, NameServer scan deferral versus Java queue rejection and related scheduling/list/wrapper differences, and omission of APIs requiring Netty/JVM objects such as `Channel`, `ChannelHandlerContext`, `ResponseFuture`, and `ChannelWrapper`. These historical classifications do not by themselves establish equivalent public capabilities or observable behavior under the current Phase 18 contract. P18-V01 must verify each Java source path and Rust representation; existing tests and source mappings remain evidence requirements.

The user also decided that support for TLS encryption algorithms or key sizes unavailable in the selected RustCrypto/rustls dependencies is not mandatory. This applies only to those provider/library capability limits; it does not waive TLS modes, trust/hostname validation, Java fixtures currently supported by the dependencies, or Phase 19 live-validation requirements.

Additional user decisions: signed negative Java time-configuration values must not be rejected merely because Rust `Duration` cannot represent them; their runtime behavior must be determined from the Java/Netty source and mapped. Rust's bounded per-connection frame `Vec` reuse is accepted as a Rust-native alternative to reproducing Netty pooled-allocator internals. Rust hook `equality_key` and lock-scoped collection access semantics are accepted instead of arbitrary Java `equals()` and unsynchronized live collection references. The latter two decisions accept only the representation/allocator differences, not missing transport behavior or unrelated Rust-only public capabilities.

The table below records Rust-shaped surfaces that lacked a distinct Java public declaration in the earlier inventory. Retain a surface only when it expresses an existing Java public capability or an agreed Rust-native representation of that capability; a Rust-only capability or setting remains a P18-V01 blocker. This is not a blanket waiver for missing behavior. Java `ChannelWrapper` reconnect/replacement behavior has been reviewed for request-generation paths: only the first GO_AWAY received on the currently cached generation may retire it and trigger retry; subsequent GO_AWAY responses from that retired generation fail without starting another replacement/retry, while already-pending requests on the retired generation may still complete. A GO_AWAY response processed after the original socket-close cleanup can still mark the old generation as retired and retry if no replacement is cached; a concurrently cached replacement is not evicted. Rust covers this with `p3_go_away_retries_once_on_a_new_connection`, `p3_go_away_replacement_keeps_other_old_connection_requests_alive`, and `p3_multiple_go_away_responses_on_retired_connection_only_retry_once`. Explicit address close and shutdown close both current and retired generations. Replacement/close interleavings remain subject to the source-backed coverage and tests listed in this inventory; they are not assumed exhaustive.

## Rust public API additions and Rust-to-Java mapping

The following Rust APIs are Rust-shaped forms or extensions without a one-to-one Java declaration. They are recorded here to make the mapping bidirectional rather than treating every Rust name as a Java method. Each surface is classified below as an adapter for existing Java behavior or an explicit Rust-native result/ownership contract; a similar name alone is not evidence of equivalence. Construction snapshots `ClientConfig`: semaphore capacities and SOCKS JSON routes are consumed while constructing `RemotingClient`; processor/callback/event workers and periodic schedulers are created at `start()`; socket options, watermarks, TLS connector, and idle timeout are applied when each connection is created; request deadlines and current listener/processor/hook registrations are consulted per operation. Mutating the caller's config after construction is impossible because it is moved into the client. Java's `NettyClientConfig` remains mutable, but `NettyRemotingClient` captures some values at construction (semaphores, callback/public executors, SOCKS routes, TLS context) and reads other values from the retained config at `start()`, connection bootstrap, or each operation. This inventory historically accepted Rust's fixed construction-time snapshot. The sync-timeout close setting now has a live adapter and post-start regression coverage. Under the current Phase 18 contract, P18-V01 must still compare the remaining Java read/update paths with Rust and resolve any observable setting mismatch; moving those Rust config values into the client does not itself close the gap.

### Exception, cause, and remark parity requiring item-by-item disposition

Java exposes checked exception subclasses and nested `Throwable` causes; Rust uses a closed `TransportError` enum. The error-class/cause/remark disposition requested by the plan is applied below: preserve original typed causes where available, retain contextual timeout information, and accept Rust-native callback and event error surfaces. These decisions do not claim Java exception hierarchy or exact remark parity.

| Java 5.5.1 path | Current Rust result / displayed remark | Disposition |
|---|---|---|
| `getAndCreateChannel*` / `invokeSync` connection failure: `RemotingConnectException("connect to <addr> failed", cause)` | `ConnectRequest { remote_addr, cause: Some(ErrorSource) }` for typed dial/TLS failures; address and typed source chain are retained. Java `NettyRemotingClient` commonly constructs this exception with null cause, so Rust's richer source diagnostic is an intentional addition, not asserted as Java cause parity. |

## Inventory conclusion

The scoped Java public interface, concrete client surface and overloads (including protected `doConnect`/`getHostAndPort`, nested handler/wrapper types, and channel-close overloads), inherited `NettyRemotingAbstract` public/protected APIs, callback/response-future, processor, event, all `NettyClientConfig` settings/accessors, relevant `NettySystemConfig` properties, TLS controls, Rust public declarations and configuration validation/defaults are enumerated against current Rust APIs and named scripted/unit tests in both directions. GO_AWAY source review now covers wrapper replacement without eagerly closing the old channel, generation-scoped retry, concurrent old-channel pending requests, multiple GO_AWAY responses on one retired generation, stale close behavior and replacement lifecycle; the old connection is retained until closure, explicit address close or client shutdown. Explicit close and shutdown both drain retired connections; request/replacement/close interleavings listed in this inventory have named regression coverage. The Rust-only public API table names the extensions found in the scoped remoting client surface; the connection-generation field and public address parser have been removed, and the private Java channel-future helper has no public Rust counterpart. Callback result metadata, executor/error traits, lock-scoped collection accessors and explicit TLS property/decryption adapters are Rust ownership/type representations of existing Java capabilities, not new wire or transport features; Java Netty/JVM types and global state are not fabricated. Rust oneway exposes connection/admission/write completion through an owned operation future, whereas Java discards most post-return transport outcomes; the earlier Phase 3 disposition treated this as an accepted Rust-native surface, and P18-V01 must confirm it remains an idiomatic representation of the same public capability without adding a feature. Inbound response writes follow Java's no-fixed-deadline behavior and terminate on connection shutdown. The config rows identify Java property seeds versus explicit Rust config and capture whether each setting is read at construction, start, per-channel creation or per operation; the sync-timeout close setting now has a live update adapter, while the other Rust `ClientConfig` snapshot rows still require P18-V01 reconciliation against Java's retained mutable config. `getNameServerAddressList()` now preserves Java's null-versus-list distinction as `Option<Vec<String>>`; empty updates still leave the prior value unchanged. Rust exposes lock-protected `with_rpc_hooks` and `with_processor_table` access to the live collections as well as hook snapshot inspection, matching mutable inspection while preventing unsynchronized aliases. Source review covers outbound hook-before-admission ordering for future/callback and oneway paths; Java `invokeSync` runs outbound hooks through virtual `invokeImpl` dispatch before async semaphore admission, now covered by `p3_sync_invoke_obeys_async_admission_and_runs_hooks_first`; sync admission-time timeout is surfaced through Java's send-request wrapper and closes the acquired channel (`p3_sync_admission_failure_maps_to_send_request_and_closes_socket`), while oneway hook timing has dedicated test `p3_outbound_rpc_hook_runs_before_oneway_admission_wait`. Public callback send status follows Java's wrapper-created default `ResponseFuture` on exceptional completion (true), even if the internal response future marked send failure; covered by scripted peer tests. Callback executor access now exposes the default effective executor and resetting the custom executor restores it, while Java executor ownership/lifecycle differences remain narrowly documented. It also covers Java inbound before-hook/pipeline/processor/after-hook branches represented by Rust typed outcomes, callback failure ordering and GO_AWAY retry branches. Java `channelNotActiveInterval` is inert in the pinned client's observed scheduled flow because its only use is a protected method without a call site; Rust no longer imposes an extra automatic close policy from that setting. Historical `PARTIAL`, `NOT MAPPED`, `NOT EQUIVALENT` and `ACCEPTED DIFFERENCE` labels retain their row-level detail, but do not by themselves satisfy the current Phase 18 contract. P18-V01 must verify that each public capability and setting maps to Java 5.5.1 and that observable behavior is equivalent. The sync-timeout close setting is closed by the live update adapter; other unresolved rows remain open. P3-V04 is Phase 3's live-server handoff and remains deferred to Phase 19. The Rust per-client TLS isolation exception is narrowly scoped to shared mutable global/reload state, not other TLS behavior. Java `getRPCHook()` and `getProcessorTable()` mutable-inspection APIs now have Rust lock-protected live collection accessors; channel-object close overloads and Netty context/framework entry points remain absent because their framework types have no Rust-native public counterpart. TLS system/config-file keys load to per-client snapshots, and a per-client decryptor can be supplied; Java's global mutable reload-at-each-context-build lifecycle is explicitly accepted as a Rust per-client isolation exception (not a RocketMQ wire/API capability), while built-in PBES1/PBES2 encrypted-key decryption covers the Java fixtures and the explicitly scoped RustCrypto/rustls supported formats.
