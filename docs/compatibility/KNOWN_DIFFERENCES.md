# Known differences and evidence gaps

## Phase 2 Remoting codec

- Java's 5.5.1 private RocketMQ serializer narrows request code and version to signed 16-bit values. The Rust private-header encoder rejects values outside that range instead of silently wrapping. JSON encoding retains full i32 request codes and is the supported path for such values. Java-generated fixture `private-large-code` documents the Java narrowing behavior; it is decoded as the narrowed signed value.
- Java's private serializer writes both absent and empty remark as a zero-length string; Rust preserves the distinction in its command model but the wire decoder returns `None` for either representation. An absent versus empty body similarly collapses to no body when the frame body length is zero.
- Java's `LanguageCode.valueOf(byte)` returns null for unknown private-header values; Rust preserves the raw byte as `LanguageCode::Unknown` rather than losing it. JSON headers use enum names and reject names Java cannot map.

- No Rust client implementation exists at the start of Phase 0; all Rust mappings are pending their owning phase.
- Java harness fixtures are offline protocol-command evidence, not live NameServer/Broker outcomes.
- Rust intentionally keeps TLS config reload state per client for isolation. Java 5.5.1 reloads `tls.config.file` into process-global mutable settings whenever a new SSL context is built, so a later client can observe a file reload while existing clients retain their old context. This is an accepted Rust-native isolation exception, not a RocketMQ wire/API capability; do not describe it as strict Java TLS lifecycle parity.
- Encrypted client PKCS#8 PEM keys are decrypted in pure Rust when `tls.client.keyPassword` is set. Supported formats include PBES1 `pbeWithMD5AndDES-CBC` (including RocketMQ Java 5.5.1's encrypted `client.key` fixture) and PKCS#8 PBES2 schemes supported by RustCrypto (AES-CBC with PBKDF2/SHA-1 or SHA-2, and scrypt; DES/3DES support is enabled only for compatibility). Other PBES1 ciphers, legacy PEM encryption headers and unsupported PBES2 algorithms remain unsupported and return a TLS error. The Java fixture's 512-bit RSA key is decrypted/parsed but cannot be loaded by the selected rustls provider; a separate 2048-bit encrypted fixture verifies provider loading. This is parsing/decryption parity; private key algorithms and minimum key sizes are additionally constrained by the selected rustls crypto provider.
- Transport lifecycle remains partially non-equivalent where Java depends on Netty thread/event-loop identity: Rust construction validates configuration and retains worker receivers; callers must invoke `RemotingClient::start()` inside an active Tokio runtime before transport operations. `start()` is idempotent; invoke APIs return `NotStarted` and address reachability is false before start. Shutdown before start discards retained receivers and prevents a later start. Java channel-event queue admission is bounded to 10001 in both, but worker scheduling and shutdown/drain differ; Tokio idle timer expiry emits/closes from the connection task and does not reproduce Netty timer scheduling precision. Fatal Rust transport/protocol failures now queue EXCEPTION then CLOSE, matching Java's exceptionCaught-triggered close lifecycle; ordinary EOF/close queues CLOSE. The default callback executor now uses a separate shutdown signal: Rust joins other owned tasks before stopping and joining callback workers, so callbacks created by pending/invoke completion during shutdown are drained rather than lost. Rust waits for owned callback work only until the shared 90-second shutdown deadline, then aborts remaining Tokio async workers and returns; unlike Java's non-blocking executor shutdown, Rust normally drains first. An already-running `spawn_blocking` callback cannot be forcibly stopped and may continue after `shutdown()` returns.
- Inbound unsupported-request responses use Java's exact ` request type <code> not supported` remark. Inbound processor, pipeline and RPC-hook failures return `SYSTEM_ERROR` with the Rust error message when available; string panic payloads are preserved and non-string panics use a generic remark. Java uses `UtilAll.exceptionSimpleDesc`, adding the exception representation and first stack frame, which Rust cannot reproduce from its current typed error contract. Response code, opaque propagation, and oneway suppression are mapped; exact exception/cause/stack metadata is not.
- Rust `ClientConfig::validate()` rejects integer settings outside their corresponding Java signed `int`/`long` ranges and semaphore capacities above Tokio's `Semaphore::MAX_PERMITS`; Java `NettyClientConfig` stores these settings as signed `int`/`long` and does not impose the Tokio-specific limit. This prevents Rust constructor panics and documents the narrower executable range. Java system properties seed selected `NettyClientConfig` defaults/fields, whereas Rust has no implicit JVM-property/environment lookup: callers provide explicit config. Rust moves a config snapshot into `RemotingClient`; Java retains a mutable config reference, so mutation after client construction can affect values read at later lifecycle stages (while constructor-captured semaphores/executors/SOCKS/TLS state stay fixed). This lifecycle/source difference is documented per setting in the Phase 3 inventory.
- Phase 3's Rust-only public API/config surface is now itemized in `PHASE_3_REMOTING_INVENTORY.md`, including context/deadline/future forms, explicit `start()`, executor and pipeline traits, typed TLS loading/decryption APIs, collection closures and address helpers. The audit is not a waiver of the plan's no-extra-public-feature rule; context metadata, public address parsing and some typed TLS/property helper surfaces remain unresolved for acceptance pending disposition after full parity review.
- Rust outbound writes now use an unbounded per-connection FIFO enqueue, matching Java `channel.writeAndFlush`'s lack of a hard pending-write capacity limit. Operation deadlines still bound the active socket write; already-enqueued frames remain ordered, and connection shutdown drops the remaining backlog. This removes the prior Rust-only queue-full admission failure, but unlike Netty a Rust send caller waits for write completion and can receive a deadline error. Loopback test `p3_inbound_responses_survive_unbounded_outbound_backlog` queues beyond the former 128-frame capacity while withholding peer reads, then verifies all inbound responses and a concurrent invoke response arrive after draining.
- Live Broker behavior, TLS/auth profiles and cross-language cases remain `PENDING_PHASE_19` until executed against a verified server artifact.
- Phase 0 harness emits selected request codes and is not yet the complete Java public API/configuration inventory; completion is required by Phases 18–19.
