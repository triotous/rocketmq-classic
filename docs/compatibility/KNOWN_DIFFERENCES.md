# Known differences and evidence gaps

## Phase 9 pull and offset validation boundary

- Pull facade, offset-store and boundary-RPC offline checks are recorded in [PHASE_9_OFFLINE_METHOD_MATRIX.md](PHASE_9_OFFLINE_METHOD_MATRIX.md). They use Java 5.5.1 source-derived fixtures and scripted peers; no live 5.3.4 Broker result is claimed. P9-V03 remains `PENDING_PHASE_19` until the Docker local integration suite runs.
- Search timestamps and response offsets are signed Java `long` values. A successful `-1` empty-queue result stays a valid value; only transport/protocol/Broker failures return an error.

## Phase 2 Remoting codec

- Java's private serializer writes both absent and empty remark as a zero-length string; Rust preserves the distinction in its command model but the wire decoder returns `None` for either representation. An absent versus empty body similarly collapses to no body when the frame body length is zero.

- No Rust client implementation exists at the start of Phase 0; all Rust mappings are pending their owning phase.
- Java harness fixtures are offline protocol-command evidence, not live NameServer/Broker outcomes.
- Rust intentionally keeps TLS config reload state per client for isolation. Java 5.5.1 reloads `tls.config.file` into process-global mutable settings whenever a new SSL context is built, so a later client can observe a file reload while existing clients retain their old context. This is an accepted Rust-native isolation exception, not a RocketMQ wire/API capability; do not describe it as strict Java TLS lifecycle parity.
- User decision: Rust is not required to extend TLS key support beyond encryption algorithms and key sizes available from the selected RustCrypto/rustls dependencies. This is limited to provider/library capability gaps, not a waiver for supported Java formats or TLS trust, hostname, mode, and Phase 19 validation behavior.
- Encrypted client PKCS#8 PEM keys are decrypted in pure Rust when `tls.client.keyPassword` is set. Supported formats include PBES1 `pbeWithMD5AndDES-CBC` (including RocketMQ Java 5.5.1's encrypted `client.key`) and PKCS#8 PBES2 schemes supported by RustCrypto (AES-CBC with PBKDF2/SHA-1 or SHA-2, scrypt, and 3DES; DES/3DES support is enabled only for compatibility). A Java 5.5.1 PBES2 + 3DES key/certificate fixture is decrypted and accepted by rustls in `java_pbes2_3des_encrypted_private_key_is_decrypted_and_loaded`; fixture SHA-256: key `401de60297e7d4edb02a585987becc3dede70fcf2e34774678473f7e81517b17`, certificate `436543da7b4d337106dd3695a2a8ddcd4c78d2a0f1e21b1a7856931af6b460c5`. Java fixture source: reference checkout `remoting/src/test/resources/certs/privkey.pem` and its matching certificate. PBES1 MD2/RC2, legacy PEM encryption headers and unsupported PBES2 algorithms remain unsupported. JDK 21 SunJCE evidence (`Cipher.getInstance`) recognizes `PBEWithMD5AndDES`, `PBEWithSHA1AndDESede`, and `PBEWithSHA1AndRC2_40`, but reports `NoSuchAlgorithmException` for `PBEWithSHA1AndDES`, `PBEWithMD2AndDES`, and `PBEWithMD5AndRC2`; Java provider selection is external and Java `TlsHelper` delegates decryption/key parsing to Netty/JCA rather than defining a RocketMQ key format. Thus the remaining PBES1 algorithm gaps are not claimed equivalent; SHA1/DES is unavailable in the tested JDK provider, while MD2/RC2 support is provider-dependent. The Java fixture's 512-bit RSA key is decrypted/parsed but cannot be loaded by the selected rustls provider; the matching 2048-bit Java PBES2 fixture verifies provider loading. This is parsing/decryption parity; key algorithms and minimum sizes are additionally constrained by the selected rustls crypto provider.
- Transport lifecycle remains intentionally non-equivalent where Java depends on Netty thread/event-loop identity. Earlier Phase 3 dispositions accepted Tokio worker identity, polling, scheduling, shutdown/drain, and executor lifecycle differences; under the current parity contract these remain acceptable only where public capabilities/settings and observable operation behavior still correspond to Java 5.5.1. The earlier inventory also treated the lower-level `RemotingClient` transport configuration snapshot as accepted against Java's mutable `NettyClientConfig`. The Phase 3 inventory now records each Remoting setting's Java read/capture boundary and its Rust adapter or snapshot behavior, including live updates and construction/start/proxy-CIDR/per-channel snapshots; this closes that timing-inventory slice only and does not waive broader P18-V01 review. Core `ClientRuntime::config()` exposes a shared mutable `ClientConfig` like `MQClientInstance.getClientConfig()` (ADR-0037). Earlier Phase 3 rows also classified queued-byte writability/watermark accounting versus Netty outbound-buffer accounting, NameServer scan deferral versus Java executor rejection and related scheduling/list/wrapper behavior, and omission of APIs requiring Netty/JVM object contracts (`Channel`, `ChannelHandlerContext`, mutable `ResponseFuture`, `ChannelWrapper`). Those historical labels do not establish parity under the current contract; P18-V01 must determine whether each has an equivalent public capability and observable result, and resolve any behavior mismatch. Rust construction validates configuration and retains worker receivers; callers must invoke `RemotingClient::start()` inside an active Tokio runtime before transport operations. `start()` is idempotent; invoke APIs return `NotStarted` and address reachability is false before start. Shutdown before start discards retained receivers and prevents a later start. Java channel-event queue admission is bounded to 10001 in both, but worker scheduling and shutdown/drain differ; Tokio idle timer expiry emits/closes from the connection task and does not reproduce Netty timer scheduling precision. The address-only `ChannelEventListener` callback contract is a Rust-native representation of the Java event capability: Rust does not fabricate a Netty `Channel` handle. Fatal Rust transport/protocol failures now queue EXCEPTION then CLOSE, matching Java's exceptionCaught-triggered close lifecycle; ordinary EOF/close queues CLOSE. The default callback executor now uses a separate shutdown signal: Rust joins other owned tasks before stopping and joining callback workers, so callbacks created by pending/invoke completion during shutdown are drained rather than lost. Rust waits for owned callback work only until the shared 90-second shutdown deadline, then aborts remaining Tokio async workers and returns; unlike Java's non-blocking executor shutdown, Rust normally drains first. An already-running `spawn_blocking` callback cannot be forcibly stopped and may continue after `shutdown()` returns.
- Inbound unsupported-request responses use Java's exact ` request type <code> not supported` remark. Inbound processor, pipeline and RPC-hook failures return `SYSTEM_ERROR` with the Rust error message when available; string panic payloads are preserved and non-string panics use a generic remark. Java uses `UtilAll.exceptionSimpleDesc`, adding the exception representation and first stack frame, which Rust cannot reproduce from its current typed error contract. Response code, opaque propagation, and oneway suppression are mapped; exact exception/cause/stack metadata is not.
- Phase 3 error parity disposition is recorded in `PHASE_3_REMOTING_INVENTORY.md`: Rust now retains typed error causes where available, GO_AWAY carries typed remote-address/generation/retry context with Java-style diagnostics, and timeouts carry phase/address/configured duration where available. Java exception hierarchy, path-specific remarks/counts and exact stack frames remain non-equivalent; the inventory describes those differences rather than claiming full exception parity.
- Rust `ClientConfig::validate()` rejects integer settings outside their corresponding Java signed `int`/`long` ranges and semaphore capacities above Tokio's `Semaphore::MAX_PERMITS`; Java `NettyClientConfig` stores these settings as signed `int`/`long` and does not impose the Tokio-specific limit. This prevents Rust constructor panics and documents the narrower executable range. Java system properties seed selected `NettyClientConfig` defaults/fields, whereas Rust has no implicit JVM-property/environment lookup: callers provide explicit config. Rust moves lower-level transport config into `RemotingClient` using the per-setting capture boundaries recorded in `PHASE_3_REMOTING_INVENTORY.md`; Java-versus-Rust property sourcing remains documented separately from setting read timing. The core runtime `ClientConfig` is mutable through `ClientRuntime::config()` and follows the audited Java live-read sites in ADR-0037.
- Historical Phase 3 dispositions accepted the listed Rust-only public APIs, an immutable construction-time config snapshot, and documented Tokio executor, callback scheduling, ownership and lifecycle differences. The current Phase 18 parity contract supersedes blanket acceptance of unmatched public APIs/settings: public capabilities and settings must correspond to Java 5.5.1, while Rust may use idiomatic types and components to express them. Recheck every inventory row and its observable behavior before closing P18-V01; P3-V04 remains deferred to Phase 19.
- Rust outbound writes now use an unbounded per-connection FIFO enqueue, matching Java `channel.writeAndFlush`'s lack of a hard pending-write capacity limit. Operation deadlines still bound the active socket write; already-enqueued frames remain ordered, and connection shutdown drops the remaining backlog. This removes the prior Rust-only queue-full admission failure, but unlike Netty a Rust send caller waits for write completion and can receive a deadline error. Loopback test `p3_inbound_responses_survive_unbounded_outbound_backlog` queues beyond the former 128-frame capacity while withholding peer reads, then verifies all inbound responses and a concurrent invoke response arrive after draining.
- Phase 3 recorded P3-V01/V02/V03/U01 as complete under its earlier dispositions. P18-V01 reopens any public API, setting, or observable-behavior row not reconciled to the current Java 5.5.1 parity contract. P3-V04 live Broker/TLS validation, TLS/auth profiles and cross-language cases remain `PENDING_PHASE_19` until executed against a verified server artifact.
- Phase 0 harness emits selected request codes and is not yet the complete Java public API/configuration inventory; completion is required by Phases 18–19.
