# Known differences and evidence gaps

## Phase 9 pull and offset validation boundary

- Pull facade, offset-store and boundary-RPC offline checks are recorded in [PHASE_9_OFFLINE_METHOD_MATRIX.md](PHASE_9_OFFLINE_METHOD_MATRIX.md). They use Java 5.5.1 source-derived fixtures and scripted peers; no live 5.3.4 Broker result is claimed. P9-V03 remains `PENDING_PHASE_19` until the Docker local integration suite runs.
- Search timestamps and response offsets are signed Java `long` values. A successful `-1` empty-queue result stays a valid value; only transport/protocol/Broker failures return an error.

## Phase 2 Remoting codec

- Java's private serializer writes both absent and empty remark as a zero-length string; Rust preserves the distinction in its command model but the wire decoder returns `None` for either representation. An absent versus empty body similarly collapses to no body when the frame body length is zero.

- No Rust client implementation exists at the start of Phase 0; all Rust mappings are pending their owning phase.
- Java harness fixtures are offline protocol-command evidence, not live NameServer/Broker outcomes.
- Java-compatible Rust TLS property sources share a process-wide retained property state, matching Java `TlsSystemConfig`; the first explicit system-property map initializes it once, even when TLS mode is Plain, and later maps do not replace those static values. `TransportMode` reads `tls.enable` and the default config path from that initial map; TLS files cannot change them, matching Java's file extractor. Every new `RemotingClient` reloads its retained file source before building the TLS connector, while existing clients keep their constructed context. Omitted file properties retain the latest process value across distinct `TlsConfig` sources. Rust still receives system properties explicitly instead of reading JVM properties implicitly. The invoked Java and Rust regressions are recorded in `PHASE_3_REMOTING_INVENTORY.md` and `docs/release-checklist.md`.
- User decision: Rust is not required to extend TLS key support beyond encryption algorithms and key sizes available from the selected RustCrypto/rustls dependencies. This is limited to provider/library capability gaps, not a waiver for supported Java formats or TLS trust, hostname, mode, and Phase 19 validation behavior.
- Encrypted client PKCS#8 PEM keys are decrypted in pure Rust when `tls.client.keyPassword` is set. Supported formats include PBES1 `pbeWithMD5AndDES-CBC` (including RocketMQ Java 5.5.1's encrypted `client.key`) and PKCS#8 PBES2 schemes supported by RustCrypto (AES-CBC with PBKDF2/SHA-1 or SHA-2, scrypt, and 3DES; DES/3DES support is enabled only for compatibility). A Java 5.5.1 PBES2 + 3DES key/certificate fixture is decrypted and accepted by rustls in `java_pbes2_3des_encrypted_private_key_is_decrypted_and_loaded`; fixture SHA-256: key `401de60297e7d4edb02a585987becc3dede70fcf2e34774678473f7e81517b17`, certificate `436543da7b4d337106dd3695a2a8ddcd4c78d2a0f1e21b1a7856931af6b460c5`. Java fixture source: reference checkout `remoting/src/test/resources/certs/privkey.pem` and its matching certificate. PBES1 MD2/RC2, legacy PEM encryption headers and unsupported PBES2 algorithms remain unsupported. JDK 21 SunJCE evidence (`Cipher.getInstance`) recognizes `PBEWithMD5AndDES`, `PBEWithSHA1AndDESede`, and `PBEWithSHA1AndRC2_40`, but reports `NoSuchAlgorithmException` for `PBEWithSHA1AndDES`, `PBEWithMD2AndDES`, and `PBEWithMD5AndRC2`; Java provider selection is external and Java `TlsHelper` delegates decryption/key parsing to Netty/JCA rather than defining a RocketMQ key format. Thus the remaining PBES1 algorithm gaps are not claimed equivalent; SHA1/DES is unavailable in the tested JDK provider, while MD2/RC2 support is provider-dependent. The Java fixture's 512-bit RSA key is decrypted/parsed but cannot be loaded by the selected rustls provider; the matching 2048-bit Java PBES2 fixture verifies provider loading. This is parsing/decryption parity; key algorithms and minimum sizes are additionally constrained by the selected rustls crypto provider.
- Transport lifecycle remains intentionally non-equivalent where Java depends on Netty thread/event-loop identity. Earlier Phase 3 dispositions accepted Tokio worker identity, polling, scheduling, shutdown/drain, and executor lifecycle differences; under the current parity contract these remain acceptable only where public capabilities/settings and observable operation behavior still correspond to Java 5.5.1. The earlier inventory also treated the lower-level `RemotingClient` transport configuration snapshot as accepted against Java's mutable `NettyClientConfig`. The Phase 3 inventory now records each Remoting setting's Java read/capture boundary and its Rust adapter or snapshot behavior, including live updates and construction/start/proxy-CIDR/per-channel snapshots; this closes that timing-inventory slice only and does not waive broader P18-V01 review. Core `ClientRuntime::config()` exposes a shared mutable `ClientConfig` like `MQClientInstance.getClientConfig()` (ADR-0037). Earlier Phase 3 rows also classified queued-byte writability/watermark accounting versus Netty outbound-buffer accounting, NameServer scan deferral versus Java executor rejection and related scheduling/list/wrapper behavior, and historical API gaps around Netty/JVM carriers (`Channel`, `ChannelHandlerContext`, `ResponseFuture`, `ChannelWrapper`). Rust now maps callback/future channel capabilities with `ResponseFuture` and identity-preserving `ChannelHandle` values. Inbound processors and request-pipeline stages receive a shared Rust `RequestContext` with channel identity, peer address, close, and no-deadline write enqueue; raw Netty objects, the rest of the handler-context surface, wrapper internals, and Tokio sockets remain framework-specific. The pinned `NettyRequestProcessor` review closes the `ChannelHandlerContext` RocketMQ-capability question: Java declares `processRequest(ctx, request)` and default `rejectRequest()`, and Rust maps them to `RequestProcessor::process_with_request_context` and `reject_request`. RocketMQ request handling uses one identity-preserving `RequestContext` with peer address, channel state, close, and typed-command writes. Allocator, handler propagation, arbitrary-object writes, promises, and raw Netty channel APIs remain framework-specific; Tokio does not emulate that Netty surface. The processor exception-remark formatting variation is accepted as diagnostic-only under the core flow-parity rule (see the inbound error row below); category, response-code, and control-flow mismatches remain open P18-V01 work. Rust construction validates configuration and retains worker receivers; callers must invoke `RemotingClient::start()` inside an active Tokio runtime before transport operations. `start()` is idempotent; invoke APIs return `NotStarted` and address reachability is false before start. Shutdown before start discards retained receivers and prevents a later start. Java channel-event queue admission is bounded to 10001 in both; polling and scheduling remain different, while shutdown now maps Java's up-to-90-second synchronous event-worker join boundary. Tokio idle timer expiry emits/closes from the connection task and does not reproduce Netty timer scheduling precision. Channel-event callbacks receive an identity-preserving Rust-owned `ChannelHandle` with peer address, state, close, and write operations; connection generation remains private transport bookkeeping. This maps the public Java channel capability without fabricating a Netty `Channel` or exposing a raw Tokio socket. Fatal Rust transport/protocol failures now queue EXCEPTION then CLOSE, matching Java's exceptionCaught-triggered close lifecycle; ordinary EOF/close queues CLOSE. Java `NettyRemotingClient.shutdown()` closes channels and requests graceful event-loop shutdown, then calls `NettyEventExecutor.shutdown()`; inherited `ServiceThread.shutdown()` joins that event thread for up to 90 seconds. It subsequently calls `ExecutorService.shutdown()` for the public and scan executors without waiting for their work to finish. Rust `shutdown().await` now keeps public-executor admission open through the same join or deadline boundary, then closes admission without waiting for accepted work; transport cleanup and accepted callbacks continue in a background task. The callback queue is signaled after transport work and the channel-event worker finish or reach the deadline, preserving queued completions. A blocking callback cannot be forcibly stopped and may continue after `shutdown()` returns. Tokio polling and cleanup scheduling remain implementation-specific.
- GO_AWAY retry follows Java `ChannelWrapper` identity. Once reconnect swaps the wrapper's current channel, another GO_AWAY response from the old channel retries through that same current wrapper; `p3_all_requests_on_retired_connection_retry_once_on_shared_replacement` checks this after observing the first retry. Java uses `tryLock`, so a callback that races before the swap can fail when the lock is held; the deterministic test does not claim every simultaneous ordering retries. See the request-generation row in `PHASE_3_REMOTING_INVENTORY.md`.
- **Accepted diagnostic difference (language-specific exception formatting):** inbound unsupported-request responses use Java's exact ` request type <code> not supported` remark. Inbound processor, pipeline and RPC-hook failures return `SYSTEM_ERROR` with the Rust error message when available; string panic payloads are preserved and non-string panics use a generic remark. Java uses `UtilAll.exceptionSimpleDesc`, adding the exception representation and first stack frame, while Rust does not reproduce that diagnostic text. The response code, request opaque, oneway suppression, processor skip/after-hook order, and terminal response path are mapped and tested. Under the project's core rule, exact Java exception text is not required when the observable flow remains aligned; the difference is recorded here and is not claimed as text-for-text compatibility.
- Pinned Java 5.5.1 inbound shutdown handling now has an explicit Rust match: after processor lookup and before `rejectRequest`, a shutting-down remoting client returns `GO_AWAY` (`1500`, `please go away`) only when the request version exceeds `MQVersion.Version.V5_3_1.ordinal()` (`475`). Unsupported request codes remain first, and version 475 remains on the existing rejection/dispatch path. The invoked Java and Rust boundary cases are recorded in `fixtures/runtime/remoting-shutdown.json`; this closes that shutdown-flow discrepancy only.
- Phase 3 error parity disposition is recorded in `PHASE_3_REMOTING_INVENTORY.md`: Rust now retains typed error causes where available, GO_AWAY carries typed remote-address/generation/retry context with Java-style diagnostics, and timeouts carry phase/address/configured duration where available. `ErrorSource` maps Java `Throwable` cause chains through Rust's `Error::source()` and typed downcast APIs; its value equality compares displayed source chains, while Java `Throwable` inherits object-identity equality. Derived Rust error equality is not used to select transport flow. Java exception hierarchy, path-specific remarks/counts and exact stack frames remain non-equivalent; the inventory describes those differences rather than claiming full exception parity.
- Remoting `ClientConfig` represents Java signed `int`/`long` settings with `i32`/`i64`, including the callback thread count; callback counts at or below zero use an effective limit of four at `start()`. Tokio bounds effective semaphore permits, with Java's signed semaphore behavior mapped where representable. Java system properties seed selected `NettyClientConfig` defaults/fields, and Rust mirrors the documented subset through matching process-environment keys when constructing defaults; callers can still provide explicit config values. Rust moves lower-level transport config into `RemotingClient` using the per-setting capture boundaries recorded in `PHASE_3_REMOTING_INVENTORY.md`; Java-versus-Rust property sourcing remains documented separately from setting read timing. The core runtime `ClientConfig` is mutable through `ClientRuntime::config()` and follows the audited Java live-read sites in ADR-0037.
- Historical Phase 3 dispositions accepted the listed Rust-only public APIs, an immutable construction-time config snapshot, and documented Tokio executor, callback scheduling, ownership and lifecycle differences. The current Phase 18 parity contract supersedes blanket acceptance of unmatched public APIs/settings: public capabilities and settings must correspond to Java 5.5.1, while Rust may use idiomatic types and components to express them. Recheck every inventory row and its observable behavior before closing P18-V01; P3-V04 remains deferred to Phase 19.
- Rust outbound writes now use an unbounded per-connection FIFO enqueue, matching Java `channel.writeAndFlush`'s lack of a hard pending-write capacity limit. Operation deadlines still bound the active socket write; already-enqueued frames remain ordered, and connection shutdown drops the remaining backlog. This removes the prior Rust-only queue-full admission failure, but unlike Netty a Rust send caller waits for write completion and can receive a deadline error. Loopback test `p3_inbound_responses_survive_unbounded_outbound_backlog` queues beyond the former 128-frame capacity while withholding peer reads, then verifies all inbound responses and a concurrent invoke response arrive after draining.
- Phase 3 recorded P3-V01/V02/V03/U01 as complete under its earlier dispositions. P18-V01 reopens any public API, setting, or observable-behavior row not reconciled to the current Java 5.5.1 parity contract. P3-V04 live Broker/TLS validation, TLS/auth profiles and cross-language cases remain `PENDING_PHASE_19` until executed against a verified server artifact.
- Phase 0 harness emits selected request codes and is not yet the complete Java public API/configuration inventory; completion is required by Phases 18–19.
- `ResponseFuture.toString()` is represented by Rust `Display` with the same stable state fields and ordering, but callback objects, nested command/error renderings, and the JVM identity hash embedded in `CountDownLatch.toString()` have no stable Rust textual equivalent. Java `waitResponse()` also throws `InterruptedException` when the waiting JVM thread is externally interrupted and clears that thread's interrupt flag; Rust's standard `Condvar` wait has no external thread-interrupt primitive. Response/timeout results and the separate `ResponseFuture::interrupt()` operation remain mapped. The Java fixture records both behaviors; Rust tests cover stable display fields, latch transition, wait timeout, response release, and the mapped future-interrupt operation. These are diagnostic/runtime representation differences, not transport-flow exemptions.
- Scheduler immediate shutdown returns pending handles for queued Rust jobs and preserves submitted-call identity, matching Java `ScheduledExecutorService.shutdownNow()` return and future-state behavior. Rust places the 30 constructor-time jobs from Java's five `StatsItemSet`s in the client scheduler queue: 10-second, 10-minute, and hourly samplers plus minute, hour, and day log jobs for each set. Samplers advance Rust metric windows, and print jobs emit `tracing::info!` events with Java's `ConsumerStatsManager` target and matching metric fields, including a 25-sample hourly day window. The pre-start Rust regression reads `fixtures/runtime/scheduled-executor-shutdown.json` and confirms the same 32 returned entries as Java with two submitted calls. The queue-count and missing-statistics-event gaps are closed. Subscriber-provided timestamp, thread, and formatting decorations remain backend-specific; broad P18-V01 reconciliation remains open.
