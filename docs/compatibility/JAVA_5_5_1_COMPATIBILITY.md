# Java 5.5.1 compatibility evidence

## Baseline

- Java client: `org.apache.rocketmq:rocketmq-client:5.5.1`
- Source tag/commit: `rocketmq-all-5.5.1` / `efa1be59d6fc747ad220f036c86030f05f0419f9`
- Server baseline: 5.3.4 (`V5_3_4`), reserved for live validation
- Source paths, artifact hashes and tool versions: `compat/java-reference/README.md`
- Status vocabulary: implementation `TODO / IN_PROGRESS / PARTIAL / UNIT_VERIFIED / COMPATIBLE`; live `PENDING_PHASE_19 / PASS / FAIL / BLOCKED`. Fixture existence is not implementation or live-server evidence.

## Phase 1 model and registry status

Phase 1 provides the initial Rust 2024 workspace (`rocketmq-classic-common` and `rocketmq-classic-protocol`), pinned to Rust 1.85.0/MSRV 1.85. The common crate contains message/property models and message/pull flags; protocol contains the full pinned 166-request/68-response integer registry, language and serialization tags, route conversion models, and heartbeat JSON models. Unit coverage cross-checks the Phase 0 fixture sidecars, Java UTF-16 queue ordering, malformed property handling, static/ordered route cases, Java-compatible JSON field names, signed values, and flag preservation. Registry and offline-fixture coverage are not client feature completion or live Broker validation.

## Phase 2 Remoting codec status

The `rocketmq-classic-remoting` crate now contains JSON and RocketMQ private-header codecs plus bounded incremental full-frame encoding/decoding. The 16 MiB maximum frame limit includes the four-byte prefix, matching Java Netty's default. Java fixture coverage includes transaction, request/reply, large request-code narrowing evidence, and optimized/ordinary `FastCodesHeader` equivalence. Maven verify also decodes two Rust-generated frames using the pinned Java client. P2-V01/V02/V03 are unit-verified; this does not represent live Broker execution or complete client compatibility. Java absent/empty remark and body distinctions that are not represented on the wire are documented in the crate codec behavior.

## Phase 3 Remoting transport status

The current Java-to-Rust and Rust-to-Java remoting API/configuration ledger, including concrete method, setting, test-ID, and non-equivalent Netty behavior mappings, is maintained in [`PHASE_3_REMOTING_INVENTORY.md`](PHASE_3_REMOTING_INVENTORY.md). This inventory records unresolved differences; it does not imply Phase 3 acceptance.

Rust remoting implements deadline-based sync-future and duration-based wrapper, async-callback and oneway APIs; async/oneway semaphore admission; TCP/TLS/SOCKS5 connection reuse; raw-code request processors with reject hook, shared default pool, and optional per-registration executor; request pipeline with remote-address/generation context, typed abort/error outcomes and RPC hooks; idle timeout, basic channel events and GO_AWAY reconnect with one retry under the original deadline; idempotent shutdown. Callback execution has configurable worker count, bounded callback queue, disable-executor mode, a caller-supplied `CallbackExecutor` matching Java `setCallbackExecutor`, inline fallback when a custom executor rejects, complete-before-success/fail ordering after channel establishment (matching Java's wrapper and ResponseFuture call chain); channel connect/TLS setup failures invoke fail without complete, as in Java and async admission waits within the operation deadline. Client config also maps Java callback/worker thread counts, socket buffer sizes, write watermarks, pooled allocator flag, idle timeout, timeout socket close and GO_AWAY/scan flags. TCP and SOCKS5 socket buffers use socket-level options; configured write high/low watermarks track queued outbound bytes with hysteresis. Enabling the Java pooled allocator option is rejected explicitly because Tokio's transport does not expose a Netty-style pooled allocator. NameServer list/read/availability, chosen-address tracking, round-robin selection and failover across configured addresses exist; availability scan runs at connect-timeout intervals. The client now exposes `is_channel_writable`, `is_address_reachable` and `close_channels`; writability uses configured queued-byte watermarks with hysteresis when present and otherwise bounded outbound queue capacity (not Netty event-loop write-buffer accounting), and reachability is an async connect operation. Tests P3-V01/V02/V03/U01 plus `p3_context_aware_pipeline_receives_connection_metadata`, `p3_pipeline_abort_preserves_java_style_code_and_message`, `p3_rpc_hook_abort_and_failures_map_to_java_response_paths`, `p3_before_hook_failure_runs_pipeline_and_after_hook_but_skips_processor` and `p3_after_hook_runs_when_processor_returns_no_response` cover terminal races, cancellation, opaque wrap, queue saturation, authenticated SOCKS5 scripted proxy, callback executor concurrency/custom-executor routing and rejection fallback, admission deadline, hook ordering, inbound dispatch/pipeline/rejection including one-way processor execution without response, default processor fallback, GO_AWAY retry, NameServer invoke/availability, channel management and socket buffer options, TLS trust/hostname and task shutdown. Scripted peers are not a live Broker. PARTIAL gaps: Java shuffles the supplied NameServer list when its membership changes; Rust now randomizes changed lists and retains duplicates, although it does not mutate the caller's list in place. Exact NameServer channel-wrapper recovery, scan-executor and cleanup semantics are not fully mapped. The newest close-channel behavior clears chosen/available state when the selected socket actually closes; `p3_nameserver_recovers_selection_after_chosen_channel_closes` covers a scripted peer close, while connected peers are kept open in selection/failover tests to avoid conflating successful response availability with later close cleanup. Callback context exposes request, response/error, send status, timeout flag and elapsed duration, and async pending-response handling waits through Java's +1-second scan grace; callback dispatch invokes complete before success/failure as Java does; send/write failures have a separate Rust `Send` variant, but the full Java exception/callback taxonomy and timeout races remain. Channel idle/last-response tracking exists; channel events use a bounded single-worker queue, not Java's `NettyEventExecutor` lifecycle/overload semantics. Per-processor/default executor lifecycle and thread semantics, actual Netty `ChannelHandlerContext`, complete Java RPC-hook abort/exception ordering and executor overload behavior remain. Java pooled allocator and worker-group switches have no equivalent Tokio controls; pooled allocator enablement is rejected rather than ignored. TLS system properties/config-file/reload/test-mode/decryption controls are not mapped; secure rustls chain and hostname verification is intentionally retained rather than copying Java's insecure test-mode defaults. The public API/config inventory is still incomplete: the source grep and current mappings identify client operations and `NettyClientConfig` settings, but no exhaustive method/overload/field/type/default/range/test-ID ledger has yet been closed in both directions. P3-V04 remains PENDING_PHASE_19. Do not claim parity until bidirectional inventory and tests are complete.

## Phase 0 evidence

The Java harness emits offline Remoting request frames for route, heartbeat, send, pull, offset query/update and lock operations. Each `.bin` has a JSON sidecar with source/client/server version labels, scenario ID, codec, code, normalized decoded fields, body length and frame SHA-256. These are protocol command fixtures, not executed RPC results. Live Broker scenarios in `tests/differential/scenarios.yaml` remain `PENDING_PHASE_19`.
