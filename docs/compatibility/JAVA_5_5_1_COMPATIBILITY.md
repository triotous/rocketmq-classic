## Phase 3 Remoting transport status

The current Java-to-Rust and Rust-to-Java remoting API/configuration ledger, including concrete method, setting, test-ID, and non-equivalent Netty behavior mappings, is maintained in [`PHASE_3_REMOTING_INVENTORY.md`](PHASE_3_REMOTING_INVENTORY.md). The inventory distinguishes mapped behavior, user-accepted differences and the Phase 19 live-server handoff; it does not claim live Broker validation.

Rust remoting implements deadline-based sync-future and duration-based wrapper, async-callback and oneway APIs; response-table scanning starts after 3 seconds and repeats every second, matching Java's nominal scan cadence and `begin + timeout + 1s` cleanup threshold; future-based invoke waits through the scanner cleanup grace while retaining its pending entry/async permit (and can accept a late response); sync invoke returns at its own wait deadline while scanner cleanup remains pending; the NameServer address-list getter preserves Java's unconfigured-null versus configured-list behavior with `Option<Vec<String>>`, and empty list updates preserve the existing configuration; async/oneway semaphore admission; TCP/TLS/SOCKS5 connection reuse; raw-code request processors with reject hook, shared default pool, and optional per-registration executor; request pipeline with owned-request input, typed abort/error outcomes and RPC hooks (including clear-all and Java-order pipeline composition); idle timeout, basic channel events with constructor-injected immutable listener and GO_AWAY reconnect with one retry under the original deadline; idempotent shutdown. Callback execution has configurable worker count, unbounded callback queue matching Java's public executor backlog, disable-executor mode (which ignores custom executors and forces inline dispatch), a caller-supplied `CallbackExecutor` matching Java `setCallbackExecutor`/`getCallbackExecutor` when enabled (with `get_callback_executor`), inline fallback when a custom executor rejects, public callback complete-before-success/failure ordering after channel establishment (matching Java `invokeAsyncImpl`'s `whenComplete` then `thenAccept`/`exceptionally` chain); initial channel connect/TLS setup failures invoke fail without complete, as in Java, and async admission waits within the operation deadline. Those initial connection failures carry Java's address-bearing connect-error category and null cause, covered by `p3_future_connect_failure_includes_java_remote_address_and_null_cause`. Client config also maps Java callback/worker thread counts, socket buffer sizes, write watermarks, pooled allocator flag, idle timeout, timeout socket close, GO_AWAY/scan flags, and the inert `maxReconnectIntervalTimeSeconds` setting (default 60; no pinned Java client read site). TCP and SOCKS5 socket buffers use socket-level options; configured write high/low watermarks track queued outbound bytes with hysteresis. The Java pooled allocator option maps to a bounded per-connection frame-buffer reuse pool, not Netty allocator semantics. NameServer list/read/availability, chosen-address tracking, randomized round-robin selection and failover across configured addresses exist; availability scan starts immediately and then runs at connect-timeout intervals, probing up to 10 configured addresses concurrently with each scan batch capped at 42 (Java scan executor equivalent: 10 maximum workers plus 32 queued jobs). Later addresses rotate into subsequent batches; Java uses `AbortPolicy` when its queue is full, while Rust defers addresses, and periodic overlap timing differs. The client now exposes `is_channel_writable`, `is_address_reachable` and `close_channels`; outbound frames use an unbounded per-connection FIFO enqueue, while writability uses queued-byte watermarks (Netty 4.1 defaults 64 KiB high / 32 KiB low unless both custom marks are positive), not Netty event-loop write-buffer accounting, and reachability is an async connect operation. Inbound response writes have no fixed activity deadline, matching Java's `writeAndFlush`; client-originated operations remain deadline-bound.
