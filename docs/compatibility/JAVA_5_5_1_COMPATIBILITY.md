# Java 5.5.1 compatibility evidence

## Baseline

- Java client: `org.apache.rocketmq:rocketmq-client:5.5.1`
- Source tag/commit: `rocketmq-all-5.5.1` / `efa1be59d6fc747ad220f036c86030f05f0419f9`
- Server baseline: 5.3.4 (`V5_3_4`), reserved for live validation
- Source paths, artifact hashes and tool versions: `compat/java-reference/README.md`
- Status vocabulary: implementation `TODO / IN_PROGRESS / PARTIAL / UNIT_VERIFIED / COMPATIBLE`; live `PENDING_PHASE_19 / PASS / FAIL / BLOCKED`. Fixture existence is not implementation or live-server evidence.

## Phase 1 model and registry status

Phase 1 provides the initial Rust 2024 workspace (`rocketmq-classic-common` and `rocketmq-classic-protocol`), pinned to Rust 1.85.0/MSRV 1.85. The common crate contains message/property models and message/pull flags; protocol contains the full pinned 166-request/68-response integer registry, language and serialization tags, route conversion models, and heartbeat JSON models. Unit coverage cross-checks the Phase 0 fixture sidecars, Java UTF-16 queue ordering, malformed property handling, static/ordered route cases, Java-compatible JSON field names, signed values, and flag preservation. Registry and offline-fixture coverage are not client feature completion or live Broker validation.

## Phase 2 Remoting codec status

The `rocketmq-classic-remoting` crate now contains JSON and RocketMQ private-header codecs plus bounded incremental full-frame encoding/decoding. The 16 MiB maximum frame limit includes the four-byte prefix, matching Java Netty's default. Java fixture coverage includes transaction, request/reply, large request-code narrowing evidence, and optimized/ordinary `FastCodesHeader` equivalence. Maven verify also decodes two Rust-generated frames using the pinned Java client. P2-V01/V02/V03 are unit-verified; this does not represent live Broker execution or complete client compatibility. Java absent/empty remark and body distinctions that are not represented on the wire are documented in the crate codec behavior.

## Phase 3 Remoting transport status

The current Java-to-Rust and Rust-to-Java remoting API/configuration ledger, including concrete method, setting, test-ID, and non-equivalent Netty behavior mappings, is maintained in [`PHASE_3_REMOTING_INVENTORY.md`](PHASE_3_REMOTING_INVENTORY.md). This inventory records unresolved differences; it does not imply Phase 3 acceptance.

Rust remoting implements deadline-based sync-future and duration-based wrapper, async-callback and oneway APIs; the NameServer address-list getter preserves Java's unconfigured-null versus configured-list behavior with `Option<Vec<String>>`, and empty list updates preserve the existing configuration; async/oneway semaphore admission; TCP/TLS/SOCKS5 connection reuse; raw-code request processors with reject hook, shared default pool, and optional per-registration executor; request pipeline with remote-address/generation context, typed abort/error outcomes and RPC hooks (including clear-all and Java-order pipeline composition); idle timeout, basic channel events with constructor-injected immutable listener and GO_AWAY reconnect with one retry under the original deadline; idempotent shutdown. Callback execution has configurable worker count, bounded callback queue, disable-executor mode (which ignores custom executors and forces inline dispatch), a caller-supplied `CallbackExecutor` matching Java `setCallbackExecutor`/`getCallbackExecutor` when enabled (with `get_callback_executor`), inline fallback when a custom executor rejects, public callback complete-before-success/failure ordering after channel establishment (matching Java `invokeAsyncImpl`'s `whenComplete` then `thenAccept`/`exceptionally` chain); initial channel connect/TLS setup failures invoke fail without complete, as in Java, and async admission waits within the operation deadline. Those initial connection failures carry Java's address-bearing connect-error category and null cause, covered by `p3_future_connect_failure_includes_java_remote_address_and_null_cause`. Client config also maps Java callback/worker thread counts, socket buffer sizes, write watermarks, pooled allocator flag, idle timeout, timeout socket close, GO_AWAY/scan flags, and the inert `maxReconnectIntervalTimeSeconds` setting (default 60; no pinned Java client read site). TCP and SOCKS5 socket buffers use socket-level options; configured write high/low watermarks track queued outbound bytes with hysteresis. Enabling the Java pooled allocator option is rejected explicitly because Tokio's transport does not expose a Netty-style pooled allocator. NameServer list/read/availability, chosen-address tracking, round-robin selection and failover across configured addresses exist; availability scan starts immediately and then runs at connect-timeout intervals, probing configured addresses concurrently. The client now exposes `is_channel_writable`, `is_address_reachable` and `close_channels`; writability uses configured queued-byte watermarks with hysteresis when present and otherwise bounded outbound queue capacity (not Netty event-loop write-buffer accounting), and reachability is an async connect operation. Tests P3-V01/V02/V03/U01 plus `p3_oneway_starts_connection_acquisition_at_call_time`, `p3_oneway_reports_invalid_address_synchronously`, client units `oneway_connection_acquisition_enters_connect_before_return` and `spawned_connection_future_is_polled_before_return`, `p3_oneway_returns_after_scheduling_before_peer_receives_frame`, `p3_outbound_rpc_hook_runs_before_oneway_admission_wait` (hook sees the unmarked request; transport marks it before admission), `p3_sync_invoke_obeys_async_admission_and_runs_hooks_first`, `p3_async_go_away_retry_callback_reports_reconstructed_request`, `p3_async_second_go_away_callback_retains_original_request`, `p3_go_away_retry_reacquires_async_admission`, `p3_nameserver_scan_probes_addresses_concurrently_and_tracks_results`, `p3_nameserver_channel_interval_has_no_implicit_scan_behavior`, `p3_context_aware_pipeline_receives_connection_metadata`, `p3_pipeline_abort_preserves_java_style_code_and_message`, `p3_rpc_hook_abort_and_failures_map_to_java_response_paths`, `p3_rpc_hooks_deduplicate_and_clear`, `p3_rpc_hook_equality_keys_match_java_contains_semantics`, `p3_outbound_hook_failures_are_not_ignored`, `p3_request_pipeline_pipe_runs_new_stage_before_existing_stage`, `p3_before_hook_failure_runs_pipeline_and_after_hook_but_skips_processor`, `p3_after_hook_runs_when_processor_returns_no_response` and `p3_go_away_retries_once_on_a_new_connection` (including Java-compatible outer after-hook arguments following retry) cover terminal races, cancellation, opaque wrap, queue saturation, authenticated SOCKS5 scripted proxy, callback executor concurrency/custom-executor routing, rejection/panic fallback, and callback panic containment, admission deadline, hook ordering including the pre-ONEWAY request view, inbound dispatch/pipeline/rejection including one-way processor execution without response, default processor fallback, Java-style GO_AWAY retry request reconstruction, NameServer invoke/availability, channel management and socket buffer options, TLS trust/hostname and task shutdown. Scripted peers are not a live Broker. PARTIAL gaps: Java shuffles the supplied NameServer list when its membership changes; Rust now randomizes changed lists and retains duplicates, although it does not mutate the caller's list in place. Removing a non-chosen address now leaves its cached channel open as Java does (`p3_nameserver_update_keeps_non_chosen_removed_connection_open`); Rust now retains removed addresses in the exposed available set until the next scan prunes them, matching Java's stale-key cleanup timing (`p3_nameserver_update_prunes_availability_on_next_scan`). Rust oneway returns `Result<Ready<Result<(), TransportError>>, TransportError>`: validation/shutdown/deadline errors are synchronous; otherwise it polls acquisition once before return, transfers pending work to an owned task and separately schedules its operation task. It does not wait for connection completion, admission or write, and dropping the result future does not cancel transmission. The first poll enters the acquire path and initiates TCP dial when this call creates the single-flight attempt, matching Java's pre-return `getAndCreateChannelAsync`/Netty `connect` dial-initiation boundary (`p3_oneway_reports_invalid_address_synchronously`). TCP connect, admission and write failures after return remain unobservable. Listener-registration exception reporting also cannot be preserved without blocking. Failures after Rust returns are not observable to the caller, and immediate semaphore saturation now maps to the Java too-much-request category, while positive-budget admission expiry maps to timeout; Java exception classes/messages and remaining timeout/shutdown error details still differ. Exact NameServer channel-wrapper recovery and scan-executor topology are not fully mapped; Rust probes concurrently and retains removed availability until scan-start pruning, but Java's per-address scheduling and wrapper lifecycle differ; Java's response-age check is in an uncalled protected scan method and Rust does not synthesize it. The configured `channelNotActiveInterval` only feeds a protected Java scan method with no call site, so Rust does not apply an automatic NameServer response-age close. The newest close-channel behavior clears chosen/available state when the selected socket actually closes; `p3_nameserver_recovers_selection_after_chosen_channel_closes` covers a scripted peer close, while connected peers are kept open in selection/failover tests to avoid conflating successful response availability with later close cleanup. Callback context exposes request, response/error, send status, timeout flag and elapsed duration, and async pending-response handling waits through Java's +1-second scan grace; public async callback dispatch invokes complete before success/failure after channel establishment, while initial connect/setup failure invokes fail only; the GO_AWAY retry connect failure follows the same complete-before-fail chain (covered by `p3_async_go_away_retry_connect_failure_completes_before_failure`); after a successful GO_AWAY retry, callback request metadata reflects Java's reconstructed retry request (`p3_async_go_away_retry_callback_reports_reconstructed_request`); retry-connect failure and a second GO_AWAY retain the original outer callback request metadata (`p3_async_go_away_retry_connect_failure_completes_before_failure`, `p3_async_second_go_away_callback_retains_original_request`). The public async callback status follows Java's wrapper-created default `ResponseFuture` (`sendRequestOK=true`) on exceptional completion, including connection/peer close; full Java timeout/shutdown/admission exception taxonomy, callback taxonomy and timeout races remain; initial connect/TLS failures carry the Java address-bearing, null-cause connect category, and post-registration frame encoding/asynchronous write failures carry the Java send-request category with no cause. Java `invokeSync` dispatches through the overridden `NettyRemotingClient.invokeImpl`, so outbound hooks run; Rust `invoke_sync` follows that virtual dispatch path, running hooks before async semaphore admission (`p3_sync_invoke_obeys_async_admission_and_runs_hooks_first`). Java `invokeSync` closes the channel on exceptional send completion (including async-admission failure), and separately applies the configured close heuristic to response timeout; these behaviors exist only on Rust `invoke_sync`. Non-sync future and async-callback response timeouts leave the channel open for reuse. Covered by `p3_u01_inflight_invoke_times_out_when_peer_does_not_reply` and `p3_sync_admission_failure_maps_to_send_request_and_closes_socket`. Channel idle tracking exists; no automatic stale-NameServer response-age close is applied because the corresponding Java protected scan method has no call site. Channel events use a bounded single-worker queue, not Java's `NettyEventExecutor` lifecycle/overload semantics. Per-processor/default executor lifecycle and thread semantics, actual Netty `ChannelHandlerContext`, Java-style `RPCHook.equals` deduplication (mapped through an opt-in equality key; custom object equality still requires an application-provided matching key) remains incomplete; Rust exposes snapshot inspection, safe removal by identity/equality key, and lock-protected live-list mutation. Java pooled allocator and worker-group switches have no equivalent Tokio controls; pooled allocator enablement is rejected rather than ignored. Java client TLS selection and trust modes are mapped through `TransportMode::from_java_properties`, `TlsConfig::from_java_properties`, `test_mode` and `auth_server`; JVM-like property maps and optional TLS config files load to a per-config snapshot, with file values overriding properties. In Java-compatible test mode, client trust/cert/key paths are ignored without file I/O or decryptor invocation, matching Java's trust-all early return. In verified mode, a per-config `PrivateKeyDecryptionStrategy` receives client role and configured password metadata. Verified chain/hostname checks remain opt-in with `test_mode: false, auth_server: true`. Java's per-context global config reload timing/ownership, strategy registration/error contract, and Netty encrypted-key behavior remain partial. The scoped public API/config inventory now enumerates Java `RemotingClient`/`RemotingService`, concrete and inherited Netty remoting declarations, `ResponseFuture`, callbacks/events, every `NettyClientConfig` getter/setter, relevant `NettySystemConfig` properties and TLS controls, plus Rust public declarations and config validation/defaults in both directions. Java's live `getRPCHook()` and `getProcessorTable()` collection inspection is represented by Rust lock-protected live collection accessors. This closes inventory coverage, not semantic parity: rows marked `PARTIAL`, `NOT MAPPED` or `NOT EQUIVALENT` remain blockers, including actual Netty channel/context contracts, TLS property/reload/password-protected-key controls, and executor/error lifecycle. P3-V04 remains PENDING_PHASE_19. Do not claim parity until bidirectional inventory and tests are complete.

## Phase 0 evidence

Each `.bin` has a JSON sidecar with source/client/server version labels, scenario ID, codec, code, normalized decoded fields, body length and frame SHA-256. These are protocol command fixtures, not executed RPC results. Live Broker scenarios in `tests/differential/scenarios.yaml` remain `PENDING_PHASE_19`.
