## Observed duplicate consumer metadata mismatch

Pinned `ConsumerData` does not override equals/hashCode. Actual `MQClientInstance.registerConsumer` accepts two distinct registration keys pointing to the same MQConsumerInner; `prepareHeartbeatData` constructs a fresh ConsumerData for each entry. Consequently equal field values still appear twice in the serialized `consumerDataSet` array. Native `ConsumerData` derives structural equality and hashes all fields, so `HashSet<ConsumerData>` collapses these values. This is an observable array multiplicity difference, not merely iteration or JVM reference identity.

Offline actual Java probe: `/tmp/p6-heartbeat-duplicate-oracle.jsh`, output `/tmp/p6-heartbeat-duplicate-oracle-reviewed.log`, pinned Maven classpath. Register `registered-a` and `registered-b`, both returning group `same`, active/cluster/last-offset, empty subscriptions and unitMode=false. Actual Java preparation reports `P6_DUPLICATE_JAVA_COUNT=2`, with two identical metadata objects. Runtime/transport never starts; construction cleanup is invoked. Initial JShell execution was denied its engine's local socket and a subsequent import ambiguity was corrected; only the reviewed no-error execution is authoritative.

Native probe `/tmp/p6-heartbeat-duplicate-rust.log`: deserialize that two-object body into existing HeartbeatData → `P6_DUPLICATE_RUST_COUNT=1`. The temporary Cargo example was removed after the probe; no debug/public feature remains. Current runtime preparation independently uses the same HashSet insertion, so outgoing data also loses equal entries.

Fixing representation must preserve multiplicity, including when V2 removes subscriptions and two formerly unequal full consumers become equal simple entries. A `Vec<ConsumerData>` can preserve the Java object-set wire multiplicity without reproducing JVM object identity, but replacing public `HeartbeatData.consumer_data_set: HashSet<ConsumerData>` affects the completed protocol model/API and downstream construction code. This is not an invented client setting and wire field names/codes need not change. The execution index requires review before changing an accepted lower-layer contract; owner confirmation is required before that public type change. No difference waiver or COMPATIBLE status is assumed.
