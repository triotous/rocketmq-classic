### ProcessQueue removal and dispatch state

The pinned Java `removeMessage` mutates only the ready `msgTreeMap`. A message
already returned by `takeMessages` lives in the separate orderly in-flight map,
so attempting to remove that message leaves the cached count and size intact;
the subsequent `commit` still returns its offset and removes it. Removing the
last ready message also leaves Java's `consuming` flag untouched, so the next
`putMessage` does not report a second dispatch until an empty `takeMessages`
clears that flag. Rust now follows both transitions while keeping its in-flight
batch ownership internal. The invoked `processQueue` fixture and
`process_queue::tests::remove_message_matches_java_for_in_flight_entries` plus
`remove_message_preserves_dispatch_state_until_empty_take` cover the behavior.
Fixture SHA-256: `67aac16425d8ac98e2d2cde4ff53a91e68b080b429711852979eb302d173dc5e`.

### `MAX_OFFSET` parse failure and pull timestamp

Java parses the last message's `MAX_OFFSET` property only after inserting the
messages and setting the dispatch flag. An invalid or overflowing value throws
`NumberFormatException` while leaving those state changes in place. Rust's
public `put_message` now returns
`ProcessQueueError::InvalidMaxOffset` after retaining the same messages,
counters and dispatch state. The invoked fixture verifies the Java exception
class, queue snapshot, and that a following valid insertion does not request a
second dispatch. The same parser error propagates through assigned queue
insertion. Java also updates `lastPullTimestamp` at the pull-request boundary,
not from `ProcessQueue.putMessage`; the Rust owner does the same, and the
fixture checks that direct insertion preserves a caller-set timestamp. Fixture
SHA-256:
`aa3a16d255ba6d331f5cb84e068db3b14e45f49c605671feebc97abc3aba8f81`.

### Empty `commit` input

Java invokes `consumingMsgOrderlyTreeMap.lastKey()` before mutating counters,
so calling `commit` without a preceding non-empty `takeMessages` throws
`NoSuchElementException` and leaves the queue unchanged. Rust's public
`commit` now returns `Err(ProcessQueueError::EmptyOrderedConsumeSet)` for this
case instead of returning `-1`; successful commits return the committed offset
in `Ok`. The invoked facade fixture compares the Java exception class and the
unchanged tree/count/size. Fixture SHA-256:
`aa3a16d255ba6d331f5cb84e068db3b14e45f49c605671feebc97abc3aba8f81`.

### `consuming` and timestamp transitions

Java sets `consuming` in `putMessage` when it starts a dispatch and clears it
only when `takeMessages` returns an empty list. A nonempty take, `commit`,
`rollback`, and `makeMessageToConsumeAgain` leave the flag unchanged. `commit`
also leaves `lastConsumeTimestamp` unchanged. Rust now preserves these public
state transitions instead of recomputing the dispatch flag or refreshing the
timestamp. The invoked fixture checks dispatch after commit, rollback, and
requeue, including a nonempty take while the flag is false, and checks the
timestamp around commit. Fixture SHA-256:
`2e43cc737fa784cdaec0488252000e82360ccd0a4b121e6ee28d2dccf704791e`.

### Duplicate offset while consuming

Java stores ready and orderly in-flight messages in separate `TreeMap`s. A
second `putMessage` for an offset already in the consuming map therefore adds
a ready entry, increments count/size, and leaves the consuming entry intact.
`commit` removes the in-flight entry and keeps the ready copy; `rollback`
overwrites that ready copy with the in-flight message without adjusting the
already-incremented counters. `removeMessage` acts on the ready copy only.
Rust now preserves both entries and these counter transitions. The fixture
checks the ready body before and after commit, rollback overwrite, removal of
the ready duplicate, and that replacing an existing ready offset does not
change Java's `queueOffsetMax`. The internal batch regression verifies that a
terminal completion leaves the repulled message ready. Fixture SHA-256:
`f4c918d58b0fd0104511281b8380a13356cd0dfb5bd1d2d370fe9b890e32bb31`.

### `clear` dispatch state

Java `clear` empties both maps, resets count/size and `queueOffsetMax`, but
leaves the `consuming` flag unchanged. Rust `clear` now preserves that flag, so
a following `putMessage` reports dispatch according to the pre-clear state.
The invoked facade fixture checks this subsequent dispatch and the cleared
count/size/tree. Fixture SHA-256:
`8ab5b2da6cd00449b2af89e5f4a3879608e00990cd2b5562cc2eef2dc23f18ff`.

### `fillProcessQueueInfo` size narrowing

Java divides the cached byte size by one MiB and narrows the `long` result to
`int`, preserving Java's two's-complement wrap. Rust now uses the equivalent
integer cast. The invoked facade fixture sets a byte count whose MiB value is
one above `i32::MAX` and compares the resulting info field. Fixture SHA-256:
`afb517bc5c6ce78f7f0d4afa0bd31f22d6fba586c8b37a3616a5b27fbf7a29de`.

### Try-unlock counter signed overflow

Java stores `tryUnlockTimes` in an `AtomicLong`; both public
`incTryUnlockTimes()` and the rebalance retry path use signed wrapping
increments. Rust now stores the value as `i64`, wraps both increment paths, and
passes the signed value through its getter, snapshot and queue-info reporting.
The isolated Java fixture seeds the counter at `Long.MAX_VALUE`, calls the
public increment, and records `Long.MIN_VALUE`; a Rust unit regression compares
the public increment, queue-info value and generation-checked retry increment
with that fixture. Fixture SHA-256:
`9b14dc24b4f3214bfb9fab7d83ebe966083685c327409c7e76b1303de63d00db`.

### Negative `takeMessages` batch size

Java constructs `new ArrayList<>(batchSize)` before reading the clock or taking
the queue lock. A negative batch size therefore throws
`IllegalArgumentException` with `Illegal Capacity: -1` and leaves
`lastConsumeTimestamp` unchanged. Rust's public `take_messages` now returns
`ProcessQueueError::InvalidBatchSize` with the same exception text before
mutating state. The invoked Java fixture and Rust facade comparison check the
error text and a seeded timestamp. Fixture SHA-256:
`63be1fa9e086d577e01c6a5ac1eba6089e30f237f9bf03b178832dc22496772d`.

### Null `containsMessage` argument

Pinned Java `ProcessQueue.containsMessage(null)` returns `false` before taking
the tree lock. Rust keeps the non-null `contains_message` method and adds
`contains_message_nullable(None)` to represent this Java input shape; the
invoked Java fixture and Rust facade comparison assert the same result.
Fixture SHA-256:
`edb43a544374bb1c5ae969bcdaa09ea3746a310b3d28dc86b459a18ecfcff551`.

### POP assignment retention

The invoked Java `RebalanceImpl.updateMessageQueueAssignment` runtime fixture
records four POP table outcomes: an expired assigned queue is dropped and
replaced; an active assigned queue remains the same object; a dropped assigned
queue remains present; and an empty assignment drops and removes the queue.
`fixtures/runtime/consumer-operations.json` records these rows in
`popRebalance` and separately records an unsubscribed POP queue being dropped
and removed by Java's topic-truncation helper. The matching Rust rebalance
regression checks table removal and retires the worker while an issued response
finishes. A PULL assignment that replaces POP keeps the existing PULL queue and
drops/removes the POP queue in both implementations. The fixture SHA-256 is
`b414477a4a64b2c252d704704a70c7b1a89f2b6a5b1014531ca0200690edda36`. Rust's
`broker_assignment_error_preserves_worker_until_empty_assignment` exercises
the owner flow against the same four expected states, including preserving the
active worker across an assignment error and removing it from the assignment
map after an empty assignment. Queue removal retires the task so an already
issued POP response can finish; the loop exits before issuing another request.
`rebalance_truncates_unsubscribed_pop_queue_and_retires_inflight_worker` covers
the unsubscribed queue cleanup branch, and
`rebalance_switch_to_pull_removes_pop_queue_and_retires_inflight_worker` covers
the POP-to-PULL transition. The
`removed_pop_queue_finishes_inflight_found_callback_before_retiring` regression
verifies that a late FOUND callback filters and ACKs a rejected message after
removal. The same response contains an accepted message; the test confirms its
consume request exits on the dropped queue without calling the listener or
ACKing it. Pull statistics and the remaining callback handling continue to
follow Java's FOUND path.

## Local rebalance route selection and lookup order

Pinned `RebalanceImpl.doRebalance(isOrder)` selects broker or local assignment
through `clientRebalance(topic)`. For Push, that method reads the consumer's
client-rebalance setting, orderly-consume state and message model; the
`isOrder` argument does not select the assignment source. It controls whether
new pull assignments request a Broker lock; Java still marks each newly
created `ProcessQueue` locked and initializes its lock timestamp before
computing the starting offset. In the clustering path Java checks for a missing
or empty route before querying consumer membership. Either case leaves current
assignments intact, notifies empty sets for non-retry topics and leaves the
balance result unchanged. A non-empty route proceeds to membership lookup.
Broadcasting with a missing route also notifies empty sets and leaves the
balance result unchanged when the callback succeeds.

Rust now selects through `client_rebalance(topic)` for clustering and
LiteSelective, handles missing and empty clustering routes before membership
lookup, and preserves these callback and balance outcomes. New Push process
queues begin locked and carry the captured initialization timestamp across
offset lookup. Evidence:
`missing_clustering_route_notifies_empty_and_keeps_assignment_without_membership_lookup`,
`empty_clustering_route_notifies_empty_and_keeps_assignment_without_membership_lookup`,
`missing_broadcasting_route_notifies_empty_and_returns_balanced`, and the
explicit `isOrder=true` broker-assignment assertion in
`client_rebalance_false_uses_broker_assignment_unless_orderly_forces_local`;
the LiteSelective broker branch is covered by
`lite_selective_rebalance_leaves_assignments_for_pop_handling`, and the
unconditional initial lock flag is checked by the client-rebalance test above.
When local membership lookup returns null or an empty list, Java leaves its
default `balanced=true` result and current assignments unchanged; a thrown
lookup error instead marks the pass unbalanced. Rust preserves this
distinction, covered by
`clustering_membership_join_leave_and_unavailable_cycles_converge` and
`unavailable_membership_keeps_the_previous_queue_assignment`.
The broader P18-V01 source and reverse API audit remains open.

## Internal implementation adaptation

The Java raw Push/Pull implementation accessors return a `RebalanceImpl`
subclass whose public methods expose live mutable process-queue, POP-queue,
subscription and topic-assignment tables, plus setters for the client factory,
strategy, message model and group. Rust maps the observable rebalance controls
to methods on the owner returned by `get_rebalance_impl`; both queue types and
live queue tables are public. Pull assignment changes populate its process
table. Pull's pinned Java implementation does not create or dispatch POP
queues; Rust matches that behavior and tests the empty Pull POP table.
Pull's model and strategy are shared with its active registration, so these
settings remain callable through the started owner and request an immediate
rebalance when changed.

One implementation call shape remains internal to Rust. Java's dispatch hooks
accept mutable internal `PullRequest`/`PopRequest` lists; Rust
creates requests through assignment activation and routes them through its
owned pull scheduler/POP workers. These differences do not remove a consumer
setting, queue operation or message-delivery flow from the public Rust facade.

Java exposes the Push implementation and its nested `RebalancePushImpl` as
separate objects. Rust's stable owner handle aliases both APIs, so it keeps
separate nullable runtime slots: `set_implementation_client_runtime` maps the
implementation's factory field, while `set_client_runtime` maps the rebalance
factory. Runtime registration and shutdown ownership remain tied to the
manager used by `start()`.

The complete pinned denominator and these implementation adaptations are
recorded. The remaining broad P18-V01 gate still covers every other Java
client source/configuration/flow row and the reverse Rust API audit.
