BatchAck is included because the pinned 5.5.1 client contains a call site. `ResetOffsetBody` and `GetConsumerStatusBody` use explicit `encode_java_json()` adapters to reproduce Fastjson's non-standard `MessageQueue` object-key syntax; ordinary Serde serialization remains standards-compliant and is not substituted for the Java body wire encoding. Model readiness does not imply that Phase 5 RPC or later public client behavior is implemented.

Phase 5 core now wires route, producer, consumer and lifecycle/extension RPC attempts to Remoting. Scripted peer tests exercise the implemented response mappings; NameServer route errors carry the selected peer address. Offline Java response fixtures currently cover selected send, pull, offset and route branches, not every method or invocation mode. Phase 5's exhaustive Java-fixture acceptance gate remains open; live Broker comparison remains Phase 19 work.

Implemented Java→Rust header fixtures live in `crates/rocketmq-classic-protocol/tests/header_inventory.rs`, `crates/rocketmq-classic-protocol/tests/headers.rs`, `crates/rocketmq-classic-protocol/tests/reply_wire.rs` and `fixtures/remoting/header-*.{bin,json}`. The inventory fails if a public header lacks a fixture or reverse assertion, and the validation matrix covers modeled fields, required/optional rules, numeric boundaries, Java booleans and unknown-field preservation. Rust-to-Java frames are generated by `cargo run -p rocketmq-classic-remoting --example generate_fixtures -- p4-headers <dir>` and `... -- p4-bodies <dir>`, then decoded by Maven `verify`. Maven checks exact ext fields for 38 Rust typed header frames and semantic JSON equality for 14 Rust typed body frames; reply V2/push frames additionally compare binary body bytes. Consumer-list absent/empty/populated and lock/unlock body cases have pinned Java fixtures and Rust decoding tests. P4-V01/V02/V03 pass; Phase 4 typed wire models are accepted, while actual RPC wiring and public client support remain later phases.

The table above is a selected checklist; `crates/rocketmq-classic-protocol/src/codes/request.rs` contains all 166 public Java RequestCode constants, and `response.rs` contains the 5 RemotingSysResponseCode plus 63 ResponseCode constants. Each file is generated/audited against the pinned Java source. Registry presence does not imply RPC implementation. See `JAVA_5_5_1_COMPATIBILITY.md` for status semantics.
