BatchAck is included because the pinned 5.5.1 client contains a call site. `ResetOffsetBody` and `GetConsumerStatusBody` use explicit `encode_java_json()` adapters to reproduce Fastjson's non-standard `MessageQueue` object-key syntax; ordinary Serde serialization remains standards-compliant and is not substituted for the Java body wire encoding. Model readiness does not imply that Phase 5 RPC or later public client behavior is implemented.

Phase 5 core wires route, producer, ordinary/Lite pull, consumer and lifecycle/extension RPC attempts to Remoting. Lite sysflag selects LITE_PULL_MESSAGE (361), otherwise PULL_MESSAGE (11), in sync and future modes. Java invoked fixtures cover 148 cases; scoped status/header/body/mode comparisons and deadline/pending tests close P5-V01/V03/U01. `PHASE_5_OFFLINE_METHOD_MATRIX.md` contains the complete method/type/branch mapping; live Broker comparison remains PENDING_PHASE_19.

Implemented Java→Rust header fixtures live in `crates/rocketmq-classic-protocol/tests/header_inventory.rs`, `crates/rocketmq-classic-protocol/tests/headers.rs`, `crates/rocketmq-classic-protocol/tests/reply_wire.rs` and `fixtures/remoting/header-*.{bin,json}`. The inventory fails if a public header lacks a fixture or reverse assertion, and the validation matrix covers modeled fields, required/optional rules, numeric boundaries, Java booleans and unknown-field preservation. Rust-to-Java frames are generated by `cargo run -p rocketmq-classic-remoting --example generate_fixtures -- p4-headers <dir>` and `... -- p4-bodies <dir>`, then decoded by Maven `verify`. Current Maven verification checks exact ext fields for 66 Rust typed header frames and semantic JSON equality for 14 Rust typed body frames; reply V2/push frames additionally compare binary body bytes. Consumer-list absent/empty/populated and lock/unlock body cases have pinned Java fixtures and Rust decoding tests. P4-V01/V02/V03 pass; Phase 4 typed wire models are accepted, while actual RPC wiring and public client support remain later phases.
