# RocketMQ Classic Rust Client

A Rust reimplementation of the Apache RocketMQ 5.5.1 Java client, with RocketMQ server 5.3.4 as the planned local/live validation baseline. Compatibility work is tracked phase by phase in [`plan/2026/09/README.md`](plan/2026/09/README.md); model and protocol status is documented in [`docs/compatibility/JAVA_5_5_1_COMPATIBILITY.md`](docs/compatibility/JAVA_5_5_1_COMPATIBILITY.md).

## Current workspace

The current workspace contains `rocketmq-classic-common`, `rocketmq-classic-protocol`, and `rocketmq-classic-remoting` (bounded codecs and a partial TCP/TLS/SOCKS5 transport). Construct a `RemotingClient` and call `start()` from an active Tokio runtime before invoking transport operations; `start()` is idempotent and constructors do not start background workers. The transport exposes async callbacks with configurable callback workers or a caller-supplied callback executor (`set_callback_executor`/`get_callback_executor`; disabled mode ignores custom executors and runs inline), sync futures, deadline-bound admission controls, request pipeline (legacy and context-aware; supports typed abort/error outcomes, Java-order stage composition via `pipe_request_pipeline`), backward-compatible fallible RPC hooks with typed abort/system-error mapping, optional Java-style equality keys for deduplication, and explicit `add_rpc_hook`/`get_rpc_hooks`/`remove_rpc_hook`/`clear_rpc_hooks` (snapshot inspection/removal without exposing a live mutable hook list), outbound hooks after successful connection establishment, Java-style pipeline/after-hook handling after a before-hook failure, and after-hook notification when a processor returns no response, exact-code/default request processors with optional per-registration executors (inbound one-way requests are processed without replies), bounded asynchronous channel/idle events, NameServer list/selection/availability scanning, reachability/writability/explicit-close helpers, configured TCP socket buffers, Java-shaped `socks_proxy_config` JSON CIDR routing, and one GO_AWAY retry that reconstructs a fresh request while preserving its code/ext fields/body. It does not claim Java 5.5.1 parity: callback context now carries the request, optional response/error, send status (Java default-true on timeout after channel establishment and false on established-channel close/shutdown/write failure), timeout flag and elapsed duration, and async response waiting includes Java's +1-second scan grace; precise Java send-failure/error taxonomy, Java-owned per-processor/default executor lifecycle/thread semantics, processor executor rejection details, full channel-event lifecycle and NameServer channel-wrapper/scan lifecycle semantics, pooled allocator, Netty worker-group controls, and TLS Java-compatible property/config-file loading and a per-client key-decryption strategy are available, but remain partial: pooled mode uses a bounded per-connection frame reuse pool, disabled worker-group mode dispatches inbound handlers on the Tokio connection task, and Java's global per-context reload timing and encrypted-key implementation semantics remain different. Rust clears chosen/available NameServer state on socket close. TLS explicitly models Java's client `tls.test.mode.enable` (default `true`) and `tls.client.authServer` (default `false`) trust behavior, including trust-all when either Java condition disables verification; set `test_mode: false, auth_server: true` for verified CA and hostname checks. The scoped Java public remoting API/configuration inventory now covers the listed public/protected client declarations, settings, TLS controls, and Rust public surface in both directions; inventory closure does not mean semantic parity, and the remaining differences are enumerated in the Phase 3 inventory. Configured write watermarks track queued outbound bytes with high/low hysteresis; they do not represent Netty's event-loop write-buffer accounting. The Rust pooled mode reuses up to four frame buffers per connection, and `disable_netty_worker_group` switches inbound dispatch to the connection task; neither reproduces Netty's allocator caches or event-loop thread lifecycle. It is pinned to Rust 1.85.0 (MSRV 1.85) and uses edition 2024. See the [compatibility matrix](docs/compatibility/JAVA_5_5_1_COMPATIBILITY.md), [Phase 3 remoting inventory](docs/compatibility/PHASE_3_REMOTING_INVENTORY.md), and ADR-0001. Producer/consumer and higher-level lifecycle features remain planned in later phases.
